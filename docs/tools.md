# Built-in tools and command sandbox

Loop registers these tools for the model by default:

| Tool | What it does |
| --- | --- |
| `list_folder` | List files and folders, optionally recursively. |
| `read_text_file` | Read bounded UTF-8 text by line or byte range. |
| `search_text` | Search selected files and folders with structured matches. |
| `write_text_file` | Write a UTF-8 file after authorization. |
| `edit_text_file` | Replace exact UTF-8 text with ambiguity checks. |
| `delete_path` | Delete an authorized file, link, or folder tree. |
| `get_current_datetime` | Return the local date and time. |
| `fetch_content` | Fetch authorized HTTP(S) text into a bounded cache. |
| `read_cached_content` | Read cached text by line or cursor. |
| `resolve_executable` | Look up a host tool and request a bounded sandbox read grant. |
| `run_command` | Run shell commands inside the host OS sandbox. |
| `inspect_command_jobs` | List owned command continuations. |
| `read_command_job` | Wait for and read bounded output from an owned job. |
| `cancel_command_job` | Request cancellation of an owned job. |
| `control_command_terminal` | Send bounded input or controls to an owned native terminal. |
| `activate_skill` | Load matching skill instructions. |
| `manage_skills` | Manage active skills and their bounded resources. |

Strict model tool schemas require nullable arguments even when unused. Supply JSON `null` (unquoted) for an unused nullable argument. Argument descriptions identify when a value is needed for a particular action or continuation mode. For optional numeric ranges in file reads, cached-content reads, and skill-resource reads, the exact strings `"none"` and `"null"` are also treated as null, regardless of case. The same applies to cached-content cursors and the file-search `include` filter; an omitted filter searches all visible files within the authorized root, while `["None"]` is a literal glob. Terminal dimensions accept the same spelling, as does terminal content for actions other than `write`. File paths, search text, skill names, and terminal input retain their literal meaning. Normal validation, access authorization, and read limits still apply.

## Edit files while a model is running

File mutations requested by an agent are checked against the source versions supplied in that model request. If you save a different version while the model is generating, Loop refuses the stale mutation before requesting approval. The tool result tells the model to reread the current file, reconsider its proposed edit, and preserve the intervening changes. When a read is authorized and complete before and after content fits the available read budget, the warning includes a bounded diff. Changes elsewhere in the same file also invalidate an edit whose exact match remains unchanged. Snapshot checks precede exact-match validation, so removed or duplicated edit anchors still produce stale-context guidance.

`read_text_file` returns a bounded text range and the SHA-256 identity of the complete source, including for empty files. Line reads automatically expand their requested byte limit to include the first line when it fits the application limit; longer lines return a bounded fragment that continues at `next_start_byte`. Results report requested and effective limits when they differ. When serialized text exceeds the result limit, Loop delivers a smaller file page with a byte continuation and caches the complete original serialized result; the top-level handle and `cached_snapshot_format` identify that snapshot. Capturing the source identity scans the whole file with bounded memory. Exact edits require their matched text to have been supplied to the model. Whole-file replacements and `replace_all` require complete visible coverage; consecutive or overlapping pages of the same version can provide it. Overlapping bytes must agree, and complete assembled content must match its source digest. Inconsistent snapshot bytes require a new read. Search results provide discovery information and require a file read before mutation. If a previously observed file is deleted during generation, a stale write cannot recreate it. The rejected write carries a trusted absence receipt, allowing the model to reconsider creation in its next request without a separate missing-file read. An explicit `read_text_file` absence report provides the same observation. Neither report authorizes another write in the original generation. Reconsidered creation still requires normal authorization and exclusively creates the file, preserving any competing recreation.

User-attached file snapshots and their cached continuations use their existing immutable versions. Reading an old cached snapshot does not refresh it from disk. The backend prepares file-bearing context before snapshot observation, preserving canonical stored history. Redacted read results and redacted or native-byte references retain their revision and existence without establishing visible source-text coverage; a newer opaque reference invalidates coverage from an older revision. A read performed in the same batch as an edit becomes usable only after its result is supplied in another model request. Successful model writes and deletions advance the known state using registry receipts. Edit receipts identify the source version; if retained ranges no longer match that source, or historical mutation arguments were redacted, Loop retains the committed revision but requires a new read rather than inventing visible bytes. Redaction of unrelated diagnostic metadata does not invalidate unchanged source content. Interrupted tool batches recover the latest matching generation view and replay completed mutations without accepting same-batch reads. Missing or inconsistent recovery history requires a new generation before file mutations, including creation. Recovery rejects ambiguous call IDs, duplicate results, and results without a matching call within one response. It never replays mutations from a later response into an older pending request. Context replay consumes at most one result per recorded call, while allowing later calls to reuse provider identifiers. Observations are reconstructed separately for each request and session; compacted summaries and legacy results without verified read receipts require another read.

These checks apply to agent file tools. Direct user commands and standalone registry calls without model observations retain their existing authorization behavior. Arbitrary shell commands write directly to the workspace and do not provide file snapshot checks. Only saved disk content is observed; unsaved editor buffers and semantic dependencies in other files are outside this protection.

## Run shell commands

`run_command` uses the host shell and works in the live workspace. Its default execution deadline is one hour; `tools.command_timeout` or `LOOP_COMMAND_TIMEOUT` can set a shorter or longer finite runtime limit. Captured stdout and stderr are limited. A timeout can still return output captured before the deadline.

The ordinary `run_command` call waits for its original supervised process and returns its result without requiring the agent to poll. After approval, native preparation has a separate 60-second ceiling; the configured runtime begins when the native process launches. Linux permits up to five seconds beyond the command deadline to deliver the bounded result and verify cleanup, including a one-second cgroup membership check. A preparation timeout prevents the command from launching. No timeout or transport failure causes Loop to replay the shell source automatically.

Set `background=true` only when the caller needs concurrent work or a separate continuation. Approval occurs within the original call; it returns an opaque `handle` after admission, and the same process continues. A command that settles before the handle is returned includes its final result when the first page contains all retained output; otherwise continue reading the remaining pages. `inspect_command_jobs` lists retained jobs owned by the selected session and their limits. `read_command_job(handle, cursor=0, wait_seconds=None)` returns at most four ordered output events and, after settlement and delivery of the retained output pages, the final result without repeated stream previews; pass each response's `next_cursor` to continue without duplication. An earlier cursor replays retained output immediately, even when a wait is requested. Otherwise, the read waits for output or completion. The default wait comes from `tools.command_job_wait_seconds` (30 seconds by default); the requested wait is capped at 90% of the current `tools.command_timeout` and the platform's supported thread wait. Set `wait_seconds=0` for an immediate poll and `include_output=true` to retrieve the original captured stream previews and tails explicitly. Interrupting a read stops that wait without cancelling the command. `cancel_command_job(handle)` requests cancellation, then inspection or reading shows the final outcome when it settles. A retry of the same persisted model call reuses its handle and never launches source again. A later model call can reuse the provider identifier and still starts a distinct job. A cursor beyond the output already produced is rejected.

On a host with a qualified native terminal capability, `run_command(interactive=true)` opens one owned pseudo-terminal and returns a session-owned handle after approval. The selected native backend declares an immutable platform capability set: Loop advertises the `interactive` argument and `control_command_terminal` tool only when terminals are supported, and `egress_origins` only when mediated egress is supported. The model-visible definitions update after native backend selection or refresh. Use `control_command_terminal` with `action=write` and `content` to send 1 to 4,096 UTF-8 bytes, `action=resize` with `rows` and `columns` from 1 to 500, `action=eof` or `action=interrupt` for canonical terminal controls, or `action=close` to cancel and forget the terminal after cleanup settles. Pending input is limited to 65,536 bytes and rejected when full. Read output and exit status with `read_command_job`; the PTY merges stdout and stderr into one stdout stream. The Linux receiver retains the master, and the macOS supervisor acquires a controlling terminal before Seatbelt applies; both expose only the slave to the sandboxed process. A shell can start an interactive sub-session, and process-created private inner PTYs work. Terminal output is returned as text with control characters visibly escaped, including ANSI and OSC sequences; Loop does not execute it as host terminal control or present it as a permission prompt. Agent-requested control arguments are removed from saved session history and routine tool display; do not put secrets in model-generated input because the model provider has already seen those arguments. The CLI also accepts direct user controls through `/call control_command_terminal handle=<handle> action=write content=<text>`; typed text is visible in the local input line. Interactive requests cannot combine with mediated egress. Ordinary noninteractive commands keep their foreground behavior.

On installed Linux, an unprivileged single-threaded command can apply an additional seccomp filter before creating threads or children through the ordinary `run_command` path. The backend declares this narrow `inner_seccomp` platform capability; it does not expose a separate model argument or grant. A filter applies to its installing thread and subsequently created children; a multithreaded runtime must synchronize existing threads and verify that synchronization succeeded before claiming a process-wide inner restriction. The filter can remove syscall access but cannot replace Loop's outer AppArmor profile, filesystem mounts, effective network scope, descriptor filter, or cgroup supervision. A nested Bubblewrap or user-namespace runtime cannot create another user namespace or mount inside this backend, so Loop does not advertise general nested-container support. On macOS, Apple's `sandbox_init` contract refuses a new profile after a process is sandboxed, and children inherit the outer Seatbelt profile; both permissive and narrower second profiles fail in the current native backend. An independently sandboxed XPC service would require a separately packaged and qualified execution backend, not a nested child retaining Loop's request boundary. Loop does not advertise an inner-sandbox capability on macOS or retry a failed nested runtime on the host. A different inner runtime requires a separately provisioned isolated environment or an explicit host request under the normal host policy.

Terminal programs may echo input into retained output and saved tool results. Optional provider response traces may also contain the model's original terminal arguments. Neither agent input nor direct CLI text should be treated as a masked secret-entry surface.

Each output event carries a stream name, content of at most 1,024 decoded characters, and a monotonic cursor. Events follow the order in which the supervisor receives chunks from the two pipes; there is no guaranteed total ordering of writes made concurrently to stdout and stderr. Live output is published only after the trusted payload-entry marker is verified and continues independently of the final result's capture limit. An older installed Linux receiver without this streaming capability requires a checked `/sandbox refresh` before a background or terminal command can start; ordinary foreground commands remain available. The per-job ring retains at most 1,000,000 UTF-8 bytes and 16,384 events; unread adjacent fragments from the same stream are coalesced while previously returned events remain stable. When older events are dropped due to either limit, a stale cursor returns `command_job.cursor_expired` with `oldest_cursor` instead of silently skipping data. Completed handles remain for up to ten minutes while the process lives. The registry keeps at most four active and eight retained jobs, and remembers at most 4,096 model call identities to prevent an evicted or expired call from replaying. New background calls with model identities are refused when that limit is reached until Loop restarts. An active job retains the selected session's native ownership lease, so switching or retiring that session is refused until the job settles; retained handles are available again when that session is selected. Handles are process-local and expire on application restart, so saved output or the workspace must be inspected before deciding whether to issue a new command.

The result's `lifecycle` separates `cancel_requested`, a known `main_process` exit, and `descendant_cleanup`. Linux reports `verified_absent` only after the authenticated receiver checks its original kernel cgroup membership; failures to complete that check remain `uncertain`. macOS retains Seatbelt confinement for detached children, but process-group signaling cannot prove that detached descendants exited, so cleanup remains `uncertain` after a command may have run. Application shutdown stops new command admission, requests cancellation, and waits up to five seconds for workers and up to five additional seconds for active native operations. It retains the selected backend while a native operation uses it and closes it when the final use settles; an unsettled worker still has uncertain cleanup. A lost Linux client connection causes the installed receiver's systemd control group to be killed, but a disconnected client cannot treat that event alone as verified cleanup. A crash invalidates process-local handles and requires recovery through inspection of saved state and the installed service.

Policy changes affect future command admission. Already-running commands may retain inherited file descriptors and network access; changing a grant does not revoke them. Cancel the owned job when an immediate stop is required, and inspect the final cleanup verdict before treating termination as established. Mediated Linux egress additionally uses its live revision lease. Loop enforces the active-job count and output and retention ceilings above. It does not currently impose per-command CPU, memory, process-count, or disk quotas on either platform; Linux uses its installed systemd cgroup for ownership and cleanup rather than resource quotas. Workspace writes can consume available disk until the host or filesystem limit intervenes.

Command streams are decoded as UTF-8 with replacement for invalid bytes. Carriage returns, line feeds and CRLF sequences are retained in newly captured output. `captured_bytes` counts the UTF-8 encoding of the retained decoded text, not the original byte count; `capture_complete` reports whether decoded characters were discarded, not whether decoding preserved the original bytes. If a stream cannot be drained, its discarded count is unknown and a normally exiting command is reported as unavailable rather than as a complete capture; retained partial output remains available. `decoding_loss` is `none` when the complete captured stream contains no replacement character; otherwise it is `unknown`, because a replacement character may be literal and discarded or undrained output may contain invalid bytes. Preview and continuation limits apply to the decoded text. If the next character exceeds the requested continuation byte limit, the reader returns that complete character and reports the requested and effective limits. Previously saved results retain their recorded content and metadata; newline normalization in earlier captures cannot be reversed, and their metadata may not include `decoding_loss`.

When a complete command stream exceeds its preview, the result also includes a bounded final excerpt with byte offsets, so status lines at the end are visible in the original result. The continuation still provides the full retained stream in order. When serialized command stream previews exceed the conversation result limit, Loop shortens the previews while preserving the command status and provides stream handles and cursors for the retained output. The top-level handle identifies the original serialized tool result, labeled `serialized_tool_result` by `cached_snapshot_format`.

Command results describe the sandbox attempt and indicate whether the attempt may have had effects. Approved host results report their own `possible_effects` separately from the sandbox attempt. When an interrupted attempt may have changed state, the result warns that it was not retried and that another attempt could repeat effects; inspect the output and state before continuing. Diagnostic metadata reports a bounded set of observed denial candidates when available, including already-buffered observations from successful commands without waiting for the diagnostic stream. Model-visible diagnostics render an unrecognized absolute resource path as `<external>`; captured command output retains its original path text. Their connection to the exit is unknown, collection may be incomplete, and a missing record does not establish that no denial occurred. A successful command may have handled denied operations. An operation also observed in a successful startup probe is identified as potentially incidental, but it can still matter to the command. The observations do not authorize access or retry a command.

For a failed command, `sandbox_diagnostics` identifies the requested command operation and logical working directory separately from any failed operation. It reports a required native capability only when a prelaunch capability check established that prerequisite; otherwise the missing right may be unknown. The failure stage and source describe where a boundary failure was reported, while `cause_confidence` remains `unknown` unless attribution is established. Recognized native denial records can supply an operation and sanitized target for each candidate, including on a successful command; truncated records do not assert a complete target. `sandbox_approval_supported` is `false` for a failed prelaunch native capability check and otherwise unknown. `next_request` names `request_host_command` only for an independently eligible no-effects host offer; it is a separate request subject to authorization, never an automatic retry.

On macOS, a backend that has passed its native enforcement probe can run when the denial stream fails to become ready or has stopped before launch; the result reports diagnostic collection as unavailable. A refused diagnostic setup, including an audit-hook veto, prevents launch and does not create a host retry offer.

Loop can recognize a system-protected loader directory from a bounded native startup probe. If the operating system does not provide a usable observation or its directory cannot be independently verified, the command remains sandboxed and the diagnostic result remains uncertain. On Linux, Loop can report kernel-journal AppArmor observations when the ordinary user can read them, a protected ELF journal reader is available, and the live receiver can be associated with the request. Missing, delayed, or inaccessible records remain unknown; restrictions enforced through hidden mount paths or seccomp may have no journal record.

Commands run offline by default. Recognized private components such as `.ssh`, `.aws`, `.config`, `.loop`, and `Library` remain protected inside granted workspace, managed temporary, skill, tool and system runtime directories, including case variants. Loop may ask for approval to:

- Read a directory outside the workspace.
- Use the network.
- Change or create Git metadata.
- Expand other sandbox access.

For `run_command`, use JSON `null` for an unused `read_roots`, `write_roots`, `executable_grant`, or `egress_origins` argument. The exact top-level strings `"none"` and `"null"` are also interpreted case-insensitively as no requested capability for these four arguments; actual list entries and other strings retain their meaning and undergo the normal validation and authorization checks.

The `read_roots` and `write_roots` command arguments request specific existing directories. Loop binds their identities, shows the actual roots in the approval, and rechecks policy before launch. A requested external write root cannot include the workspace, private host components, or Loop's configured policy and state roots; the native sandbox still denies protected workspace control paths. A `read_only` command cannot request write roots. Use `read_only=true` only when the command and its subprocesses need no workspace writes; tests and builds often write coverage, caches, or reports. This option makes the workspace read-only and Loop does not silently relax it or rerun a failed command. A hard read or write limit denies an outside root without prompting. Built-in read-root limits are approval-controlled, including unchanged legacy copies of those defaults; customized legacy roots and other saved limits without classification metadata remain hard. `/permissions limit list` displays each collection's value, classification and source. A trusted user can deliberately change a collection with `/permissions limit classify workspace read-root approval` or the corresponding write-root, network-origin and session forms; changing a collection's values makes it hard again.

A sandbox command's `network: true` requests a general native grant, not a destination or origin grant. Loop refuses it without prompting while the effective `private-network` limit is `deny` or the effective origin list lacks `*`, because that broad native grant cannot enforce those hard limits. A user who intends general access can explicitly run `/permissions limit set workspace private-network allow` (or select session scope) and, if needed, add `*` to network origins before requesting the command again. General access can reach private host and network services and is still subject to a separate command approval. Existing workflows that used a general network approval under the default private-network limit now receive this policy-change guidance instead of running. A separately authorized host request is evaluated under host policy and never follows automatically from the denial.

On a qualified Linux or macOS installation, `egress_origins` requests a list of exact HTTP or HTTPS origins such as `["https://packages.example.org"]` instead of general networking. Each origin contains a scheme, host, and optional port, without a path, query, fragment, credentials, or wildcard. Loop checks the normal network permission and the effective origin limit for every origin. The native sandbox keeps direct networking isolated and exposes an attempt-private proxy to compatible clients; the trusted mediator resolves names, filters private, link-local, and host-local addresses and locally routed aliases, and pins one allowed IPv4 address per connection. Linux uses an HTTP proxy inside the attempt's private network namespace. macOS uses an exact-path Unix SOCKS5 proxy on an owned RAM filesystem that the command cannot write; it sets the standard proxy environment variables for the command. The default private-network hard limit remains active. A `network: true` request and `egress_origins` cannot be combined. Approval applies only to the current command scope and does not authorize an automatic host retry.

The mediator forwards visible HTTP GET, HEAD, and POST requests with a bounded body and checks each new request and redirect destination. Linux HTTPS uses an opaque CONNECT tunnel and macOS HTTPS uses an opaque SOCKS tunnel: Loop checks the target host and port when a new tunnel opens, but cannot inspect encrypted redirects, domain fronting, or traffic sent inside that tunnel. It refuses stronger origin policies that require those guarantees. DNS is resolved by the mediator, without granting the sandbox direct DNS or UDP. On macOS, at most 64 lookups can remain outstanding across all mediators in the Loop process; when that limit is reached, new connections are denied until a lookup returns. A stalled system resolver can retain a worker after its mediator closes, and closure is reported uncertain if the worker has not settled by shutdown. Mediated IPv6, UDP, QUIC, SSH, raw sockets, and clients that ignore the configured proxy are unavailable; a client may also need its own supported proxy and certificate configuration. On macOS, system curl and Apple Git can use the Unix SOCKS path for HTTP(S); the qualified `uv` 0.13.6 client cannot connect to that path. For dependency retrieval on that combination, fetch approved artifacts with curl and install from local files with `uv --offline`, or use an independently authorized broader network environment. This gap does not trigger a host retry. An approved endpoint can receive arbitrary data and forward it elsewhere, so an origin grant is meaningful authority to disclose data to that endpoint.

When requesting additional sandbox access, the model can provide a `reason`. The approval prompt shows that explanation and the requested paths, executables, and network or Git scope to the user.

For a recognized safe executable named directly in a command, Loop verifies the executable found on `PATH` and can grant access to that file alone. Its directory and neighboring files remain inaccessible. Other tools may need their installation directories. When Loop cannot identify the required scope in the original call, `resolve_executable` accepts one name or a list of the tools needed by the project and returns a separate result and reference for each available tool. Pass the applicable references to `run_command`. Verified package directories can be added automatically; other directories require separate read approval, which can include neighboring files. Lookup does not run the tools or infer which indirect tools a command will invoke. Commands still run inside the sandbox.

For an unambiguous system `make` invocation, Loop can inspect selected literal phony recipes and their prerequisites to prepare the identified indirect tools in the same call. Initial no-op workspace directory changes, safe descriptor redirections, and pipelines with simple literal stages are recognized without changing the command. Workspace interpreter discovery shares a bound of 128 selections across the selected recipes. It follows supported literal interpreter chains, but does not infer a tool selected only from a recipe wrapper’s arguments. Dynamic build rules, environment settings that alter make selection, potentially mutating redirections, complex shell sequences, and selections beyond that bound use the normal explicit-scope behavior; inspect possible effects before retrying a command.

A literal `timeout` or `gtimeout` invocation with a numeric duration can also identify its child command in the original call. Loop requests approval for identified child installation and runtime folders that are not already authorized. Timeout options, expanded durations, assignments used as the child, and ambiguous child paths do not supply automatic discovery.

Loop can also inspect a bounded session scratch script selected as a literal `$TMPDIR` argument to a verified system shell. Simple literal commands can use the same managed-tool and project-runtime discovery as direct commands. Complex shell constructs and ambiguous selections are left to normal explicit-scope behavior. Inspection is advisory; the script can change before execution, and its contents do not authorize host execution, Git writes, or additional manual grants.

For an already requested or granted read root, Loop can prepare directory aliases needed by symlinked `PATH` entries even when a child process selects the executable. Discovery examines up to 1,024 directory entries and 128 matching candidates per command, prioritizing non-system `PATH` directories while preserving executable lookup order. It does not authorize other roots or neighboring data. If an indirect alias falls outside those bounds, a supported explicit executable lookup and reference can identify it for the original scope; inspect the result and any possible effects before another execution.

A workspace script selected directly, or named by a literal path or filename argument relative to the command's working directory, can also use an absolute `#!` interpreter outside `PATH` when its runtime root is requested and approved. When a directly selected script identifies an interpreter through a directory symlink, Loop can request that directory's target together with other requested read roots in the original call; this grants reads to neighboring files in that directory. A workspace-selected executable or interpreter linked directly to an external file can suggest the file's containing directory. A directly selected workspace executable can suggest a linked external directory when no explicit read root was supplied. An existing root that covers the executable or interpreter is reused. If support files lie outside the identified directory, they require a separately approved scope. For a command sequence, automatic root identification covers a literal leading script path, including a wholly quoted path; it does not infer new roots from later commands or shell-expanded executable words. It also follows a literal first argument when an unchanged, complete workspace POSIX-shell launcher consists solely of a quoted `exec` forwarding that argument, including a launcher that prefixes it with `./`. An otherwise unchanged launcher that executes one literal executable with optional literal arguments can also identify that executable, whether it forwards all arguments or discards them. Discarded arguments do not identify additional runtime roots. A forwarded executable name is selected using the inherited `PATH` in order only when the invocation preserves that `PATH`; an explicit executable path does not depend on it. A chain of launchers that forward all arguments can be followed while the selected argument prefix remains literal. Other launchers need an explicit root when their runtime cannot otherwise be identified. Loop inspects at most 4,096 bytes of each candidate single-link script and prepares aliases into the approved root in the same call. It follows bounded workspace interpreter chains; the operating system must also support executing the chain. Argument paths and filenames are discovery hints, not authorization; shell-expanded arguments and further runtime roots are not inferred.

For a selected workspace script with a simple ASCII `#!/usr/bin/env NAME` or `#!/usr/bin/env -S NAME` shebang, Loop can identify `NAME` through the unchanged inherited `PATH`, preserving its order and requesting any needed runtime scope before launch. An explicit interpreter path containing `/` is resolved from the command's working directory without searching `PATH`. The `-S` form may include simple literal interpreter arguments. The name or path must end within the first 126 bytes after `#!`, because some kernels truncate longer interpreter lines. Environment assignments, expansion, quoting, escapes, and other `env` options require an explicit scope when the runtime is not otherwise available. The operating system's `env` implementation must support the shebang form used by the script.

The bounded shell-forwarding discovery also works through these `env` forms when the selected executable resolves to Loop's system shell. Direct system-shell shebangs can include one `-e`, `-f`, or `-u` option group or `--`; the `env -S` form also supports multiple such option groups. The complete shebang must fit within the first 126 bytes after `#!`. A different executable, even one with the same name, is not treated as that shell; other options use the usual explicit-scope path when needed.

On macOS, a workspace environment can contain an interpreter link to an external installation. If Loop cannot identify the interpreter from the command, include the environment's executable directory on Loop's inherited `PATH`, resolve the interpreter and supply its scoped reference. A different interpreter found earlier on `PATH` does not authorize the environment's target. A dependency manager may also need an already prepared environment or a separately approved network grant to refresh its build dependencies.

For selected macOS runtimes with usable Homebrew installation metadata, dependency discovery also supports custom prefixes and separately located package stores. Metadata identifies candidate directories; it does not by itself authorize reading them.

For a directly selected `uv run` project command with supported literal options, Loop can identify an existing workspace environment and its linked runtime whether or not the environment is on inherited `PATH`. It recognizes the default `.venv` or a literal workspace-local `UV_PROJECT_ENVIRONMENT` and requests an identified runtime directory in the original call. Literal environment assignments and an initial directory change that leaves the working directory unchanged are also recognized when they do not make runtime selection ambiguous. Linux validates a user-local CPython runtime using its environment metadata; macOS can identify the directory when the selected installation has a usable directory symlink. When a selected runtime belongs to a verified installed package, its declared runtime dependencies can be included in the same read approval. Approval includes neighboring files in those directories; discovery does not alter `PATH`. Ambiguous options, external environments, unsupported project configuration, and versions Loop cannot match fall back to the existing behavior without an inferred runtime grant.

The same preparation can apply when the command directly selects a workspace CPython environment interpreter, or when an identified workspace script's shebang selects one. Direct path spellings such as `"$WORKSPACE_ROOT/.venv/bin/python"` and `"$WORKSPACE_ROOT"/.venv/bin/python` are recognized. The selected interpreter may have any executable name. Loop recognizes supported managed and standard `venv` metadata, uses that metadata and the bound executable identity as candidate evidence, and still requires the appropriate runtime scope approval. A separate `file` or `readlink` probe does not select the interpreter for execution and does not request its external runtime scope; inside the sandbox it may therefore report the link as missing even when an approved interpreter command can run.

Other project virtual-environment workflows backed by a user-local CPython runtime may need an explicit interpreter reference. Put the environment's `bin` directory on Loop's inherited `PATH` before starting Loop, look up the interpreter with `resolve_executable`, and pass its `grant_reference` with any other tool references to `run_command`. For a typical `.venv`, start Loop with `PATH="$PWD/.venv/bin:$PATH" loop`; use the actual environment directory if it differs. Changing `PATH` only inside a later shell command is too late for lookup. Loop validates the interpreter and environment identities and requests scoped approval for the external runtime installation, including neighboring files in that root. A selected interpreter may use any name; if the environment lacks its conventional interpreter alias, automatic runtime discovery requires the versioned CPython executable named by the environment metadata to identify the same file. Other interpreters and runtime dependencies can require their own explicit read roots. If a runtime is not visible, a dependency manager may try to replace an existing environment rather than use it; inspect the result before retrying a command that could have changed files.

The sandbox writes directly to the checkout. Concurrent commands can change the same workspace and session working files, and Loop does not roll back shell changes. On macOS, approved roots containing hardlinked regular files are refused. On Linux, ordinary linked files remain readable and executable, but become read-only; large sets can make their containing directories read-only too. Links to protected or private files found in the approved roots are refused.

For a read-only workspace, configure each tool's own output, cache and environment updates to use session scratch or disable those updates. Loop does not set tool-specific options automatically.

Use `$WORKSPACE_ROOT/...` for workspace files and `$TMPDIR/...` for the conversation's private working files. For example, run `printf draft > "$TMPDIR/report.txt"`, then call `read_text_file` with `path: "$TMPDIR/report.txt"`. Saved shell scripts use those same quoted variables. Programs read `WORKSPACE_ROOT` and `TMPDIR` from their inherited environment and pass the resulting paths to subprocesses; standard temporary-file APIs use the same session directory. Loop leaves command source and saved program text unchanged. File tools accept the declared prefixes and physical host paths within the configured workspace, session or active skill roots. They perform no general environment expansion, reject traversal outside those roots and apply the same permission and identity checks to either spelling. A Linux sandbox namespace path can differ from the host path; use the declared prefix when the two do not match. `/tmp` is an operating-system pathname; the Linux private mapping described below has session retention, while other uses remain outside that guarantee. Files persist across commands, turns, interruptions, and saved-session resumes on the same machine. Starting or switching conversations selects an isolated directory without removing earlier files. Saved-session working directories live in a database- and workspace-specific namespace beside the session database and are retained when Loop exits; in-memory library stores retain files only for the store's lifetime. Session exports do not include working-file contents, but recorded tool results can contain working-file data. Library integrations must keep session storage outside shared workspace or approved read roots to retain isolation between conversations. Durable generation bindings prevent silent recreation when bound data is missing or unsafe; such sessions fail with an explicit recovery error. Valid existing directories are adopted in place without copying. Fresh agent-data generations allow ordinary basenames such as `.loop`, `.ssh`, and `Library`; existing restricted generations keep their private-name restrictions until explicitly discarded. Native link checks, workspace controls, and outside-root protections remain active. Copy deliverables into the workspace.

The `/skills/<name>` root returned when a skill is activated addresses files through the file tools; it is not a shell pathname. Shell commands that access a skill use its physical path with the normal read authorization and native restrictions.

On Linux, eligible fresh session scratch has a separate private `/tmp` subtree. A file written as `/tmp/report.txt` is available to later commands at that path and to file tools as `$TMPDIR/loop-conventional-tmp/report.txt`. The subtree shares the session's retention, discard and filesystem storage limits; Loop does not impose a separate quota. The private mapping is unavailable for restricted or unbound scratch and when it would overlap an approved workspace, tool or runtime path. An existing unsafe or shared backing directory is refused. On macOS, literal `/tmp` does not refer to the private session directory, and sandboxed access to the host's shared temporary files is denied by default. Use `"$TMPDIR/..."` for portable temporary files.

The command environment sets `HOME`, `TMPDIR` and `XDG_CACHE_HOME` to session-private scratch paths so compatible tools can find writable home, temporary and cache storage without accessing shared host directories. On macOS, the sandbox denies the system directory-helper service that would otherwise select the host's shared temporary directory; the private environment supports developer-tool shims and build tools that read a makefile from standard input. Programs that require the denied service rather than accepting these standard paths may be unavailable within the sandbox. Tools invoked by a build may still need their own executable grants.

Native advisory ownership locks serialize cooperating harness operations on the same saved session; independent sessions can run concurrently. Recovering abandoned interactions requires ownership, so a competing loader cannot revoke a live request. Blocking prompts and confirmations retain the selected session's ownership through durable settlement, including idle command requests. Cancellation during registration or while input is pending revokes the matching request without granting a late approval; ownership remains held until revocation settles. Ordinary idle input still permits session selection. Locks close on exec and live outside the command-writable leaf. Ownership does not revoke old writable descriptors. Library callers can retire working files with `SessionManager.discard_working_directory()`; it commits a fresh generation before cleaning the validated retired root and reports incomplete cleanup. Child processes inherit the sandbox restrictions. Linux verifies descendant cleanup before returning a successful result. When its native receiver observes a full client disconnect during spawn or supervision, it exits; systemd sends SIGKILL to remaining service processes, and installation capacity remains reserved until the cgroup is empty. A lost client connection does not itself establish cleanup. On macOS, detached children can outlive command completion and cleanup while retaining their restrictions. Neither deletion, reopening nor an ownership lock establishes descendant termination or an exclusive-writer guarantee. Working files are ordinary retained filesystem state, without an atomic snapshot of them and the conversation database.

If the Linux receiver observes control input while spawn is stalled, it exits after a brief grace period, including when the client has half-closed its write side. An empty write half-close is not cancellation. The client reports an uncertain outcome because the receiver cannot confirm cleanup.

Logical path metadata reduces incidental disclosure of host locations, but does not guarantee path secrecy. Captured command stdout and stderr are preserved in previews, continuations and recorded tool results, subject to capture and decoding limits; commands such as `pwd` can expose physical paths to the model. File contents, user input and approved communication can also contain paths or other sensitive data. Existing credential filtering at the model boundary still applies; a command stream changed by that filtering has `payload_redacted: true` in the model-facing result, while the stored result remains unchanged. Previously saved results and continuations remain as recorded; their original output cannot be recovered if it was rewritten. The sandbox shares the host kernel and provides less isolation than a virtual machine. It does not protect against a malicious program already running outside the sandbox under your account, or impose strict limits on command memory use or process counts. Offline commands can still disclose readable data through output sent to the model or permitted local communication. A general `network: true` grant allows general connections; a mediated origin grant applies only at the visible HTTP request or HTTPS tunnel boundary described above.

Loop asks before running common direct destructive shell commands, but it cannot predict every effect of arbitrary shell source. Commands that have workspace write access can change existing files without a separate prompt for each file.

If the sandbox fails, Loop reports the failure in the command result. Some eligible failures with no possible command effects can offer a separate host retry, which runs without the OS sandbox and requires host-process eligibility and its own approval or an applicable exact session retry approval. Declining keeps the original command result. A completed command or a failure that may have had effects never initiates a host retry offer based on a diagnostic. If sandboxed capabilities cannot satisfy a request, the model may explicitly call `request_host_command` with the exact command and a reason. The host boundary asks for one fresh human decision per request by default, even when generic process policy allows execution; an exact human-approved session, workspace, or user host grant can instead authorize a later explicit request without prompting. The same host prompt offers these grant scopes and one-time approval; durable grants reside in the validated user policy. Host-process eligibility remains separate, and an interactive user can enable the session gate and approve the exact request during the same tool call when that gate is the only block. Under trusted YOLO mode, a separately issued explicit host request can pass that user-controlled gate without changing it or prompting; the user still sees a nonblocking host-boundary notice, and a failed sandbox attempt is never automatically retried on the host. Each host request warns that previous attempts may have had effects and that another run may repeat them. The result identifies host authority even without an interactive surface. Headless and automatic input cannot supply a fresh host decision. Console approval requires terminal input; other interaction adapters must explicitly provide fresh human host decisions. Loop trusts the configured interaction adapter and terminal input; terminal presence alone does not establish who supplied an answer. A Linux installation that fails verification never offers an unrestricted retry.

| Platform | Enforcement |
| --- | --- |
| macOS | Startup checks that Seatbelt allows a workspace write and blocks a protected read and an outside write. |
| Linux | Requires an authenticated native installation and an enforcement probe. Loop checks the installation before each command. |

Sandbox availability depends on the operating system’s enforcement capabilities and a successful startup check. Loop refuses sandboxed execution when those requirements are not met.

## Manage the Linux sandbox

The interactive Linux app provides `/sandbox` commands. Check status before running commands that depend on native enforcement:

```text
/sandbox status
/sandbox status details=true
```

The first command gives a short installed, not installed, or needs attention result. The detailed form inventories managed paths, systemd units, and loaded AppArmor profiles. It is read-only and does not authorize removal. If Loop cannot safely inspect part of the installation, it reports that part as unknown.

| Command | Effect |
| --- | --- |
| `/sandbox install` | Set up a fresh installation, cleaning authenticated partial state first. |
| `/sandbox refresh` | Alias for reinstall. Reviews removal and installation separately. |
| `/sandbox uninstall` | Remove an authenticated, idle installation. |
| `/sandbox reinstall` | Run uninstall, then install, with separate consent for each step. |

These management commands require fresh consent, a real terminal, and administrator authentication. The responsive UI first requests exclusive terminal access; press Enter or use `/respond` to hand it over. The normal editor stays suspended until the management operation settles, and the operation still requires its own fresh consent. Library and headless calls cannot elevate, and setup does not install OS packages. Refresh verifies its replacement helper before removing the current generation and stops if removal fails. You can retry after a failure; Loop verifies the current installation before proceeding. Recorded uninstall does not need a helper download. Recovery of a partial installation without a management record checks any protected staged helper and the remaining files against the package being reviewed; if other files belong to another package version, retry with the original package before updating. Loop refuses removal when descendants are running, native state is ambiguous, files have changed, or private inventory cannot be verified. An incomplete operation is reported as a management failure with attempted steps, a short reason, and current status; native execution remains unavailable until setup is healthy.

The Linux runtime needs a fixed Bubblewrap 0.12.0 or newer, enforcing AppArmor, libapparmor, libseccomp, Python 3, and systemd/cgroup v2, together with the host's policy parser and management tools. Stock Ubuntu 24.04 supplies an unsafe Bubblewrap 0.9; on Ubuntu 24.04 `x86_64` and `aarch64`, `/sandbox install` downloads the reviewed Ubuntu 26.10 Bubblewrap 0.12 package before asking for consent or administrator authentication. Loop verifies Ubuntu's signed release and package index with the protected Ubuntu archive keyring, checks the package and executable against Loop's provenance manifest, checks ELF architecture and host compatibility, and passes only the verified executable to protected setup. The download needs access to the official Ubuntu archive and fails closed when unavailable; privileged setup does not fetch code or install system packages. An administrator-provided, root-protected fixed helper at `/usr/local/bin/bwrap` takes precedence. Loop copies the selected helper into its own root-owned installation and leaves `/usr/bin/bwrap` and the distribution package untouched. The installation restores volatile policy and service state after reboot. Ordinary compatible Loop updates do not require another installation; Loop distributors maintain the managed helper manifest and must ship a reviewed update when its source becomes unsuitable. Applying a new managed helper or repairing invalidated native authority requires the normal confirmed `/sandbox refresh`; uninstall removes only the authenticated Loop generation and never changes the Ubuntu package. Recorded uninstall works without archive access. An unrecorded partial installation is removed only when its protected files match the reviewed catalog; otherwise Loop leaves them for administrator inspection. Loop uses separate file descriptors for repeated mount sources. Workspaces with many protected or private entries may exceed the operating system's open-file limit; Loop refuses mount preparation before starting the command when that limit is exceeded. Loop does not automatically run the command on the host. Offline commands use a separate network namespace, and only selected system resolver and certificate files are exposed.

On qualified Linux, an ordinary offline command can use IPv4 and IPv6 TCP and UDP loopback with its own descendants in one private network namespace. Start the server and client in the same command attempt; a later command gets another namespace. That namespace has no host or external network interface, route, bridge, forwarding path, or host proxy. A user `local-network deny` limit or administrator `deny_local_networks` restriction prevents the payload from creating IPv4 or IPv6 sockets. If exact HTTP(S) mediated egress is approved at the same time, the payload may create only IPv4 stream clients for its trusted attempt-bound loopback proxy; `bind`, `listen`, IPv6, and UDP remain denied. The proxy checks approved destinations independently and does not grant access to host-local services. A general network grant is unavailable while local networking is denied because it would expose host loopback. These local controls require an installed receiver with the matching native filter; refresh an older installation before using a local deny.

Linux sandboxed commands can use `NETLINK_ROUTE` for interface discovery. Other socket families and netlink protocols are unavailable, including VSOCK and userspace netlink, even when network access is approved. Pathname and abstract Unix-domain socket creation and datagram socket pairs are unavailable; ordinary pipes and connected Unix stream and sequenced-packet socket pairs remain available. The private network namespace isolates abstract Unix names; filesystem and socket-family controls deny access to host Unix sockets. An installation without these socket-family restrictions refuses sandboxed execution and requires a checked `/sandbox refresh` to install the protected enforcement update. On qualified macOS, an ordinary offline command can bind and connect to pathname Unix stream and datagram sockets beneath `LOOP_LOCAL_SOCKET_DIR` without a separate approval. Loop creates that private directory on an owned 8 MiB RAM filesystem separate from the workspace and scratch, so an agent cannot relocate a host socket into the allowed path. Configure tools to place their sockets there; ordinary `$TMPDIR` remains session scratch and is not a socket endpoint. Unix socket paths retain macOS's length limit, so tools using long socket names may need a shorter name. The directory is removed after the attempt, and a later attempt cannot connect to it. The path rule denies agent-origin connections to host Unix sockets, host IP loopback and external IP destinations; a user or managed local-network deny removes the local socket grant. A host process that learns the private path may connect inbound to a sandbox listener. This does not grant the sandbox access to host services and does not authenticate the peer for any protocol that needs peer identity. An unsandboxed host peer that knows the private path can deliberately pass a file descriptor to the sandbox. That host-origin delegation is outside the agent-origin isolation guarantee; applications requiring peer identity must authenticate it themselves. If the host cannot qualify the RAM filesystem and a native Unix exchange, Loop omits the local capability while ordinary offline commands remain available. An abrupt Loop termination can leave the RAM filesystem mounted until it is safely ejected or the host reboots. An interrupted or unverified setup can also leave an unmounted RAM image; Loop ejects it only after checking its unique registry marker and disk identity. The current macOS backend does not offer scoped TCP or UDP loopback, since a general loopback grant can reach host services. An explicitly authorized general network grant has that broader reach.

Linux sandboxed commands cannot use `recvmsg` or `recvmmsg` because those calls can receive file descriptors with host authority. Some programs use them for ordinary network data: for example, `dig` over UDP fails inside the sandbox, while `dig +tcp` works when network access is approved.

Linux preserves a selected, authenticated system executable's `/etc/alternatives` link without exposing the rest of that directory. A selected system link that needs another unmounted path cannot be prepared; requesting an authorized scope that contains the required path may make it available.

Automatic boot recovery requires the `/run` filesystem to support unnamed temporary files and atomic `linkat` publication. If those facilities are unavailable, Loop cannot restore the installation and refuses sandboxed execution.

Loop versions from before that transition use an older snapshot-matching rule and can reject the new installation even when their command protocol is unchanged. Use an updated Loop client with the new installation; refreshing the healthy installation solely for an older client would replace the new architecture.

Removal refuses while sandboxed commands or their descendants are live. An attempted removal can still block new commands and invalidate results from commands already running. After commands finish, retry removal or refresh in the main app. Loop keeps those commands confined and does not retry them automatically.

Linux creates request-specific sandbox profiles and automatically reclaims them after their owning Loop service and its descendants have exited. Completed requests do not accumulate toward the profile limit. When all slots are occupied by live commands, a new request waits within its existing deadline for capacity. Temporary contents remain isolated and search copies remain read-only. Loop protects its own workloads during profile retirement; another application must not transition its processes into Loop's managed profiles, because removing such a profile can leave those processes unconfined.

## Search files

`search_text` searches folder contents or selected files. It supports smart-case literal matching, regular expressions, case control, Git-style globs, neighboring lines, and a global result limit. Folder searches honor ignore rules, skip binary files and symbolic links, and return paths relative to the selected folder.

When trusted ripgrep is available, Loop runs it with fixed arguments inside a read-only native sandbox. The helper receives only the files selected and authorized by the file tool; it cannot browse other workspace or private files. Otherwise, Loop uses a bounded Python regex matcher. The two matchers have different regex dialects. Patterns are limited to 1,000 characters and searches to 30 seconds; long lines and results can be truncated. A changed native authority causes search to fail instead of switching to the Python matcher.

The optional `tools` extra installs ripgrep in the workspace virtual environment for shell commands. That workspace-writable binary is not trusted as a helper for public search.

## File and web results

Direct file tools use the permissions of the process running Loop. `list_folder` follows `.gitignore` and `.agentignore` when discovering files, but an explicit file request can name an ignored path. Text reads report source size, range, truncation, and continuation position. Results larger than 20 KiB are stored outside conversation history and returned as a preview with a `read_cached_content` handle.

Web fetches require authorization and do not follow redirects implicitly. Cached web handles keep their source metadata when a session resumes. After a handle expires, fetch the content again with new network authorization. Other cached artifacts stay local to the process.
