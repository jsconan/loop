# Built-in tools and command sandbox

Loop registers these tools for the model by default:

| Tool                       | What it does                                                                                        |
| -------------------------- | --------------------------------------------------------------------------------------------------- |
| `list_folder`              | List files and folders, optionally recursively.                                                     |
| `read_text_file`           | Read bounded UTF-8 text by line or byte range.                                                      |
| `search_text`              | Search selected files and folders with structured matches.                                          |
| `write_text_file`          | Write a UTF-8 file after authorization.                                                             |
| `edit_text_file`           | Replace exact UTF-8 text with ambiguity checks.                                                     |
| `delete_path`              | Delete an authorized file, link, or folder tree.                                                    |
| `get_current_datetime`     | Return the current local time, UTC instant, and timezone offset.                                    |
| `fetch_content`            | Fetch authorized HTTP(S) text into a bounded cache.                                                 |
| `read_cached_content`      | Read cached text by line or cursor.                                                                 |
| `resolve_executable`       | Check executable availability and identify any additional read access.                                       |
| `run_command`              | Run shell commands inside the host OS sandbox.                                                      |
| `inspect_command_jobs`     | List owned command continuations.                                                                   |
| `poll_command_job`         | Wait for an owned command to complete and return its status with available stdout and stderr pages. |
| `read_command_output`      | Immediately read another page when a poll page is not enough.                                       |
| `cancel_command_job`       | Request cancellation of an owned job.                                                               |
| `control_command_terminal` | Send bounded input or controls to an owned native terminal.                                         |
| `activate_skill`           | Load matching skill instructions.                                                                   |
| `manage_skills`            | Manage active skills and their bounded resources.                                                   |

`request_host_command` is additionally advertised when the trusted direct-host setting is enabled and host policy permits the tool. It requests a separate unrestricted command with exact approval; it is hidden by default.

Strict model tool schemas require nullable arguments even when unused. Supply JSON `null` (unquoted) for an unused nullable argument. Argument descriptions identify when a value is needed for a particular action or continuation mode. For optional numeric ranges in file reads, cached-content reads, and skill-resource reads, the exact strings `"none"` and `"null"` are also treated as null, regardless of case. The same applies to cached-content cursors and the file-search `include` filter; an omitted filter searches all visible files within the authorized root, while `["None"]` is a literal glob. Terminal dimensions accept the same spelling, as does terminal content for actions other than `write`. File paths, search text, skill names, and terminal input retain their literal meaning. Normal validation, access authorization, and read limits still apply.

## Read the exact time

Call `get_current_datetime` with an IANA timezone such as `Europe/Luxembourg` or `UTC`, or a signed fixed offset such as `+05:45`. Omit `timezone` or pass JSON `null` to use the default. The clock uses the effective `context.timezone` override when supplied, then the trusted client timezone, then host local time. In the CLI, `/call get_current_datetime timezone=Europe/London` selects a zone for that call.

The result contains `datetime`, `utc`, `timezone`, `utc_offset`, and `weekday` for one captured instant. A fixed offset returns `timezone: null` and has no daylight saving rules. A host offset is returned with `timezone: null` when the IANA name is unavailable. Invalid names, bare time abbreviations such as `CST` and `EST`, and malformed offsets produce a structured argument error. Existing stored clock results retain their original value.

The clock accepts timezone identifiers and offsets. For a place name, the agent chooses the corresponding timezone first and asks for the region when the place is ambiguous or spans multiple zones. The clock performs no outbound lookup. Routes without a verified request suffix use it for the current date and time to preserve the prompt prefix.

## Edit files while a model is running

File mutations requested by an agent are checked against the source versions supplied in that model request. If you save a different version while the model is generating, Loop refuses the stale mutation before requesting approval. The tool result tells the model to reread the current file, reconsider its proposed edit, and preserve the intervening changes. When a read is authorized and complete before and after content fits the available read budget, the warning includes a bounded diff. Changes elsewhere in the same file also invalidate an edit whose exact match remains unchanged. Snapshot checks precede exact-match validation, so removed or duplicated edit anchors still produce stale-context guidance.

`read_text_file` returns a bounded text range and the SHA-256 identity of the complete source, including for empty files. Line reads automatically expand their requested byte limit to include the first line when it fits the application limit; longer lines return a bounded fragment that continues at `next_start_byte`. Results report requested and effective limits when they differ. When serialized text exceeds the result limit, Loop delivers a smaller file page with a byte continuation and caches the complete original serialized result; the top-level handle and `cached_snapshot_format` identify that snapshot. Capturing the source identity scans the whole file with bounded memory. Exact edits require their matched text to have been supplied to the model. Whole-file replacements and `replace_all` require complete visible coverage; consecutive or overlapping pages of the same version can provide it. Overlapping bytes must agree, and complete assembled content must match its source digest. Inconsistent snapshot bytes require a new read. Search results provide discovery information and require a file read before mutation. If a previously observed file is deleted during generation, a stale write cannot recreate it. The rejected write carries a trusted absence receipt, allowing the model to reconsider creation in its next request without a separate missing-file read. An explicit `read_text_file` absence report provides the same observation. Neither report authorizes another write in the original generation. Reconsidered creation still requires normal authorization and exclusively creates the file, preserving any competing recreation.

User-attached file snapshots and their cached continuations use their existing immutable versions. Reading an old cached snapshot does not refresh it from disk. The backend prepares file-bearing context before snapshot observation, preserving canonical stored history. Redacted read results and redacted or native-byte references retain their revision and existence without establishing visible source-text coverage; a newer opaque reference invalidates coverage from an older revision. A read performed in the same batch as an edit becomes usable only after its result is supplied in another model request. Successful model writes and deletions advance the known state using registry receipts. Edit receipts identify the source version; if retained ranges no longer match that source, or historical mutation arguments were redacted, Loop retains the committed revision but requires a new read rather than inventing visible bytes. Redaction of unrelated diagnostic metadata does not invalidate unchanged source content. Interrupted tool batches recover the latest matching generation view and replay completed mutations without accepting same-batch reads. Missing or inconsistent recovery history requires a new generation before file mutations, including creation. Recovery rejects ambiguous call IDs, duplicate results, and results without a matching call within one response. It never replays mutations from a later response into an older pending request. Context replay consumes at most one result per recorded call, while allowing later calls to reuse provider identifiers. Observations are reconstructed separately for each request and session; compacted summaries and legacy results without verified read receipts require another read.

These checks apply to agent file tools. Direct user commands and standalone registry calls without model observations retain their existing authorization behavior. Arbitrary shell commands write directly to the workspace and do not provide file snapshot checks. Only saved disk content is observed; unsaved editor buffers and semantic dependencies in other files are outside this protection.

## Run shell commands

The harness exposes only arguments supported by the selected native backend. Transport instructions in the model-visible argument descriptions come from that backend and describe its usable endpoint and clients directly; the model does not select an operating-system branch. Backend refresh updates these descriptions together with capability availability. A request still requires ordinary policy approval and native admission.

`run_command` runs POSIX shell text in the live workspace. Use `.` to source POSIX scripts and invoke the required interpreter explicitly when a script uses other syntax. Loop reports the shell's exit status, so let verification failures propagate. Its default whole-command runtime limit is one hour. Set the finite positive deadline with `tools.command_job_runtime_limit_seconds` or `LOOP_COMMAND_JOB_RUNTIME_LIMIT_SECONDS`. The native result envelope retains at most 1,000,000 decoded characters per stream, while an independent observer writes the complete drained stdout and stderr to private process-local spool files. This envelope limit does not discard observed command output. When a completed command has more captured output, the preview includes a `next_tool_call` with the `read_cached_content` arguments for the next page. If output cannot be spooled, including when the filesystem is full, Loop requests cancellation and reports `command_output.capture_failed`. Successfully written output remains available while the application process is alive. A timeout can still return output captured before the deadline.

After admission, `run_command` waits for the original supervised process for `tools.command_default_initial_wait_seconds` by default (10 seconds when unset). Set `wait_seconds` to change this first wait. Loop caps a longer initial or polling request at the configured per-call maximum and keeps the original process deadline. `poll_command_job` uses `tools.command_default_poll_wait_seconds` by default (30 seconds when unset). Both calls share the independently configurable `tools.command_max_wait_seconds` cap (60 seconds by default, at most 3,600 seconds); the model schema reflects its current value. Each default must be no greater than the cap. If the process settles during the initial wait, the call returns its result; otherwise it returns a job handle and output handles for the same process. Expiry of a wait neither stops nor restarts the command. The separate configured runtime limit stops the process when its whole-job deadline expires. After approval, native preparation has a separate 60-second ceiling; the configured runtime begins when the native process launches. Linux permits up to five seconds beyond the command deadline to deliver the bounded result and verify cleanup, including a one-second cgroup membership check. A preparation timeout prevents the command from launching. No timeout or transport failure causes Loop to replay the shell source automatically.

Approval occurs within the original call. A native failure returns its sandbox result without host replay. Use `wait_seconds=0` when an immediate continuation is needed. `inspect_command_jobs` lists owned jobs, their elapsed time, captured runtime limits, byte counts, and output handles. `poll_command_job(handle, wait_seconds=None)` waits only for job completion or timeout; output arriving during the wait never ends it early. Each poll returns one bounded page from both stdout and stderr along with lifecycle status. Pass `stdout.next_cursor` and `stderr.next_cursor` from the prior result to continue without repeating output; a missing cursor means that stream has reached its current captured end. If capture is incomplete, the amount of output beyond that end is unknown. `read_command_output(handle, stream, cursor=null, max_bytes=...)` returns another immediately available UTF-8 page from `stdout` or `stderr` when the poll pages are not enough. If a cursor is at the current end while the job is running, use that same cursor again later to read newly captured output. The per-job output is stored in files instead of an expiring event ring, so unread output does not disappear as the process runs. `read_cached_content` can continue a stream from its returned artifact handle after the command-job handle expires. `cancel_command_job(handle)` requests cancellation; use polling or inspection to see when cleanup settles. Each new `run_command` call starts a new job. Completed calls remain in session history and are not repeated during recovery. Interrupted calls may resume under the normal recovery and approval rules. A cursor beyond the output currently produced is rejected.

On a host with a qualified native terminal capability, `run_command(interactive=true)` opens one owned pseudo-terminal and returns a session-owned handle after approval. The selected native backend declares an immutable platform capability set: Loop advertises the `interactive` argument and `control_command_terminal` tool only when terminals are supported, and `egress_origins` only when mediated egress is supported. The model-visible definitions update after native backend selection or refresh. Use `control_command_terminal` with `action=write` and `content` to send 1 to 4,096 UTF-8 bytes, `action=resize` with `rows` and `columns` from 1 to 500, `action=eof` or `action=interrupt` for canonical terminal controls, or `action=close` to cancel and forget the terminal after cleanup settles. Pending input is limited to 65,536 bytes and rejected when full. Read status and output pages with `poll_command_job`; pass each stream's returned cursor to continue. Use `read_command_output` when more output pages are needed. The PTY merges stdout and stderr into one stdout stream. The Linux receiver retains the master, and the macOS supervisor acquires a controlling terminal before Seatbelt applies; both expose only the slave to the sandboxed process. A shell can start an interactive sub-session, and process-created private inner PTYs work. Terminal output is returned as text with control characters visibly escaped, including ANSI and OSC sequences; Loop does not execute it as host terminal control or present it as a permission prompt. Agent-requested control arguments are removed from saved session history and routine tool display; do not put secrets in model-generated input because the model provider has already seen those arguments. The CLI also accepts direct user controls through `/call control_command_terminal handle=<handle> action=write content=<text>`; typed text is visible in the local input line. Interactive requests cannot combine with mediated egress.

On installed Linux, an unprivileged single-threaded command can apply an additional seccomp filter before creating threads or children through the ordinary `run_command` path. The backend declares this narrow `inner_seccomp` platform capability; it does not expose a separate model argument or grant. A filter applies to its installing thread and subsequently created children; a multithreaded runtime must synchronize existing threads and verify that synchronization succeeded before claiming a process-wide inner restriction. The filter can remove syscall access but cannot replace Loop's outer AppArmor profile, filesystem mounts, effective network scope, descriptor filter, or cgroup supervision. A nested Bubblewrap or user-namespace runtime cannot create another user namespace or mount inside this backend, so Loop does not advertise general nested-container support. On macOS, Apple's `sandbox_init` contract refuses a new profile after a process is sandboxed, and children inherit the outer Seatbelt profile; both permissive and narrower second profiles fail in the current native backend. An independently sandboxed XPC service would require a separately packaged and qualified execution backend, not a nested child retaining Loop's request boundary. Loop does not advertise an inner-sandbox capability on macOS or retry a failed nested runtime on the host. A different inner runtime requires a separately provisioned isolated environment or a separate direct-host request under the trusted gate and host authorization policy.

Terminal programs may echo input into retained output and saved tool results. Optional provider response traces may also contain the model's original terminal arguments. Neither agent input nor direct CLI text should be treated as a masked secret-entry surface.

The separate stdout and stderr spools preserve each stream in the order received after the trusted command-entry marker is verified; concurrent writes across the two streams have no guaranteed total order. Native observer frames are delivered independently of the bounded final result envelope. `read_command_output` pages at most the tool content byte limit at a time and does not wait for new output. There is no per-stream capture or cursor-ring ceiling; available filesystem space is the practical storage limit. If a stream cannot be drained, `capture_complete` is false and its remaining size is unknown. Output spools and their artifact handles are private and process-local; they remain available until application exit. Command-job handles expire after ten minutes. The registry keeps at most four active and eight retained jobs. Job handles are bound to their original scratch generation. An active job retains the selected session's native ownership lease, so switching or retiring that session is refused until the job settles; retained handles are available again when that session is selected.

Job inspection and reads report `elapsed_seconds` from admission until the job settles, including native preparation and cleanup, and `runtime_limit_seconds` reports the captured hard execution limit. Elapsed time is `null` before admission and for a job that fails before admission; it is not the command's precise native runtime. Polling returns once the job settles or its wait expires; output pages are read separately, and the final status summary omits stdout and stderr content.

Standalone registries without a session manager use the permission manager's own scratch directory and hold its ownership lease until the command settles. A standalone command whose instructions point at independently owned scratch is refused before launch; bind the instructions to the permission manager's scratch or provide the matching session owner. A registry cannot change session ownership while command handles are active or retained.

The result's `lifecycle` separates `cancel_requested`, a known `main_process` exit, and `descendant_cleanup`. Linux reports `verified_absent` only after the authenticated receiver checks its original kernel cgroup membership; failures to complete that check remain `uncertain`. macOS retains Seatbelt confinement for detached children, but process-group signaling cannot prove that detached descendants exited, so cleanup remains `uncertain` after a command may have run. Application shutdown stops new command admission, requests cancellation, and waits up to five seconds for workers and up to five additional seconds for active native operations. It retains the selected backend while a native operation uses it and closes it when the final use settles; an unsettled worker still has uncertain cleanup. A lost Linux client connection causes the installed receiver's systemd control group to be killed, but a disconnected client cannot treat that event alone as verified cleanup. A crash invalidates process-local handles and requires recovery through inspection of saved state and the installed service.

Policy changes affect future command admission. Already-running commands may retain inherited file descriptors and network access; changing a grant does not revoke them. Cancel the owned job when an immediate stop is required, and inspect the final cleanup verdict before treating termination as established. Mediated Linux egress additionally uses its live revision lease. Loop enforces the active-job count, retained-job count, and job-handle lifetime above. It does not currently impose per-command CPU, memory, process-count, or disk quotas on either platform; Linux uses its installed systemd cgroup for ownership and cleanup rather than resource quotas. Command output spools and workspace writes can consume available disk until the host or filesystem limit intervenes.

Command streams are decoded as UTF-8 with replacement for invalid bytes. Carriage returns, line feeds and CRLF sequences are retained in newly captured output. `captured_bytes` counts the UTF-8 encoding of the retained decoded text, not the original byte count; `capture_complete` reports whether the complete decoded stream reached its spool, not whether decoding preserved the original bytes. If a stream cannot be drained, its discarded count is unknown and a normally exiting command is reported as unavailable rather than as a complete capture; retained partial output remains available. `decoding_loss` is `none` when the complete captured stream contains no replacement character; otherwise it is `unknown`, because a replacement character may be literal and discarded or undrained output may contain invalid bytes. Preview and continuation limits apply to the decoded text. If the next character exceeds the requested continuation byte limit, the reader returns that complete character and reports the requested and effective limits. Previously saved results retain their recorded content and metadata; newline normalization in earlier captures cannot be reversed, and their metadata may not include `decoding_loss`.

When a complete command stream exceeds its preview, the result also includes a bounded final excerpt with byte offsets, so status lines at the end are visible in the original result. The continuation still provides the full retained stream in order. When serialized command stream previews exceed the conversation result limit, Loop shortens the previews while preserving the command status and provides stream handles and cursors for the retained output. The top-level handle identifies the original serialized tool result, labeled `serialized_tool_result` by `cached_snapshot_format`.

Command results describe the sandbox attempt and indicate whether the attempt may have had effects. When an interrupted attempt may have changed state, the result warns that it was not retried and that another attempt could repeat effects; inspect the output and state before continuing. Diagnostic metadata reports a bounded set of observed denial candidates when available, including already-buffered observations from successful commands without waiting for the diagnostic stream. Model-visible diagnostics render an unrecognized absolute resource path as `<external>`; captured command output retains its original path text. Their connection to the exit is unknown, collection may be incomplete, and a missing record does not establish that no denial occurred. A successful command may have handled denied operations. An operation also observed in a successful startup probe is identified as potentially incidental, but it can still matter to the command. The observations do not authorize access or retry a command.

For a failed command, `sandbox_diagnostics` identifies the requested command operation and logical working directory separately from any failed operation. It reports a required native capability only when a prelaunch capability check established that prerequisite; otherwise the missing right may be unknown. The failure stage and source describe where a boundary failure was reported, while `cause_confidence` remains `unknown` unless attribution is established. Recognized native denial records can supply an operation and sanitized target for each candidate, including on a successful command. Truncated records do not assert a complete target. On macOS, a failed command can wait briefly for records beyond the startup observations. Delayed or missing native records leave the cause unknown. `sandbox_approval_supported` is `false` for a failed prelaunch native capability check and otherwise unknown. When the trusted host setting permits it, a typed no-effects unavailable or denied result may name `request_host_command` as a separate next request. A nonzero exit alone does not prove sandbox incompatibility. No diagnostic authorizes host execution.

On macOS, a backend that has passed its native enforcement probe can run when the denial stream fails to become ready or has stopped before launch; the result reports diagnostic collection as unavailable. A refused diagnostic setup, including an audit-hook veto, prevents launch and does not create a host retry offer.

Loop can recognize a system-protected loader directory from a bounded native startup probe. If the operating system does not provide a usable observation or its directory cannot be independently verified, the command remains sandboxed and the diagnostic result remains uncertain. On Linux, Loop can report kernel-journal AppArmor observations when the ordinary user can read them, a protected ELF journal reader is available, and the live receiver can be associated with the request. Missing, delayed, or inaccessible records remain unknown; restrictions enforced through hidden mount paths or seccomp may have no journal record.

Commands run offline by default. Recognized private components such as `.ssh`, `.aws`, `.config`, `.loop`, and `Library` remain protected inside granted workspace, managed temporary, skill, tool and system runtime directories, including case variants. Loop may ask for approval to:

- Read a directory outside the workspace.
- Use the network.
- Change or create Git metadata.
- Expand other sandbox access.

Ask for the project operation in chat. Loop prepares the scope before execution and shows whether the command can write project files. Choose **Allow once** for this run or **Deny** to decline. When available, a remembered approval covers the same reviewed scope. **Show full scope** and **Show reduced scope** toggle the details. The agent requests additional runtime services only for a command that needs them.

Loop recognizes executable links in a project’s local tool installations and can suggest installed programs mentioned by a directly selected shell launcher. The approval shows each additional readable directory, including its neighboring files. The prepared request includes the runtime paths it identified. Already approved installation roots can supply the stable directory aliases used by the linked tools. Discovery inspects bounded, readable project paths and does not execute project code. Dynamic command names and nonstandard installation layouts may require a separately selected runtime. An uninstalled dependency or incompatible interpreter still needs to be supplied by the project environment.

For `run_command`, use JSON `null` to omit `read_roots`, `write_roots`, `write_files`, `executable_grant`, `runtime_services`, or `egress_origins`. The exact top-level strings `"none"` and `"null"` are also treated as omissions, regardless of capitalization. List entries and other strings undergo normal validation and authorization.

The `read_roots` and `write_roots` command arguments accept lists of specific existing directories. Omit both write arguments to let Loop prepare the scope under the owner's workspace policy. Use `write_roots: "scratch"` to explicitly keep directory writes in private scratch. Saved tasks retain their declared write lists. Loop binds their identities, shows the actual roots in the approval, and rechecks policy before launch. A requested external write root cannot include the workspace, private host components, or Loop's configured policy and state roots. The native sandbox still denies protected workspace control paths. An explicit directory or file scope replaces the ordinary preference. Use `["$WORKSPACE_ROOT"]` for an explicit whole-checkout scope, or name an existing output subdirectory for narrower writes. Command results show the writable directories in `write_scope.roots`. `git_write` separately requests Git metadata authority. Creating a repository also requires the workspace in the requested directory write scope. Loop does not relax a denied scope or automatically replay a failed command. A hard read or write limit denies an outside root without prompting. Built-in read-root limits are approval-controlled, including unchanged legacy copies of those defaults. Customized legacy roots and other saved limits without classification metadata remain hard. `/permissions limit list` displays each collection's value, classification and source. A trusted user can deliberately change a collection with `/permissions limit classify workspace read-root approval` or the corresponding write-root, network-origin and session forms. Changing a collection's values makes it hard again.

Use `write_files: ["$WORKSPACE_ROOT/.coverage"]` to create, update, or remove just that file on a backend that advertises exact file writes. A workspace-relative path such as `.coverage` also works. The parent must be a real existing directory. Admission accepts an absent entry or a single-link regular file and rechecks both the entry and parent before launch. `write_scope.files` reports the selected names. macOS confines the grant to regular files. Linux grants authority at the exact name and applies the target's own permissions when following any symlink created there during execution. A subsequent exact-file request refuses an existing symlink. An older Linux installation requires `/sandbox refresh` to offer this capability. [Save an exact write grant](permissions.md#sandbox-paths).

Tools can create sidecars, caches or temporary files beside their named outputs. Configure them to use `$LOOP_OUTPUT_DIR` for private output, or request a dedicated existing directory in `write_roots` for outputs that belong in the checkout. Each of these scopes lets the checkout remain read-only elsewhere.

### Saved verification tasks

Ask Loop to run a project's tests in chat. It uses the project's documented commands through the ordinary sandbox and asks for permission as required. A fresh workspace can run checks immediately.

For an owner-operated shortcut, save the exact command under a name and run it when needed. The saved command uses private session scratch and leaves the checkout read-only by default, including in a workspace that permits ordinary commands to write.

```text
/verify save checks './scripts/check'
/verify run checks
```

The shortcut name starts with a lowercase ASCII letter or digit and can contain up to 64 lowercase letters, digits, underscores or hyphens. `/verify list`, `/verify show NAME` and `/verify remove NAME` manage the private shortcuts. To replace one, save the same name again. Saving a command grants no process consent. At launch Loop checks its current definition, shows the command and requested resources for any required approval, and reports its normal result or job handle. If the shortcut returns a running job, ask for its progress or output in the same conversation.

For a shortcut that needs a specific working directory, environment or output scope, `/verify save` also accepts a shell-quoted JSON object. `command` is required. `cwd` defaults to `$WORKSPACE_ROOT`. `environment` adds literal values to the command’s environment. `read_roots`, `write_roots` and `write_files` use normal command permission checks. Use an exact file or a bounded output directory for results that belong in the checkout. The command result’s `scratch.output_path` gives the location of private outputs for retrieval through the file tools.

For long-running checks, keep progress visible while retaining the full report. With an approved stock Bash, `bash -o pipefail -c './scripts/check 2>&1 | tee "$LOOP_OUTPUT_DIR/check.log"'` streams the output to the current job and saves it in private scratch. A failed check produces a nonzero exit even when `tee` succeeds. When a poll reports that the job is running, keep polling that handle through quiet intervals until the supervisor reports completion or the configured deadline.

When a command fails with write-denial or permission evidence, `write_scope.retry` explains how to keep the requested command and its checks. For a relevant fixed output path, merge `arguments_to_merge` into the original `run_command` arguments when present. Its `write_files` contains the previous exact file scopes and eligible paths from native write-denial observations. Native creation denials that suggest a group of generated siblings or a sidecar of a declared exact file lead to private output or a dedicated write directory. Use the same approach for caches. Check for effects before issuing another command. Each attempt is independently authorized under the current policy.

An executable whose visible path and resolved target are both covered by the backend’s system runtime roots needs no additional read grant, including aliases between those roots. On Linux, an additional read root that exactly repeats an authenticated read-only system runtime root reuses that runtime boundary. It does not turn the runtime inventory into a workspace data scan. Workspace and writable roots, and separately requested runtime subdirectories, still undergo the data alias checks; repeating a system root grants no extra write authority and does not remove protected-path denials.

Use `egress_origins` with `network: false` for exact HTTP(S) destinations on a backend that supports mediated egress. A command requesting both exact origins and general networking is refused before approval. A sandbox command's `network: true` requests a general native grant. Loop refuses it without prompting while the effective `private-network` limit is `deny` or the effective origin list lacks `*`, because that broad native grant cannot enforce those hard limits. A user who intends general access can explicitly run `/permissions limit set workspace private-network allow` (or select session scope) and, if needed, add `*` to network origins before requesting the command again. General access can reach private host and network services and is still subject to a separate command approval. Existing workflows that used a general network approval under the default private-network limit now receive this policy-change guidance instead of running. A separately authorized host request is evaluated under host policy and never follows automatically from the denial.

On a qualified Linux or macOS installation, `egress_origins` requests a list of exact HTTP or HTTPS origins such as `["https://packages.example.org"]` instead of general networking. Each origin contains a scheme, host, and optional port, without a path, query, fragment, credentials, or wildcard. Loop checks the normal network permission and the effective origin limit for every origin. The native sandbox keeps direct networking isolated and exposes an attempt-private proxy to compatible clients; the trusted mediator resolves names, filters private, link-local, and host-local addresses and locally routed aliases, and pins one allowed IPv4 address per connection. Linux uses an HTTP proxy inside the attempt's private network namespace. macOS uses an exact-path Unix SOCKS5 proxy in a fresh sealed directory whose socket and ancestry the command cannot write or relocate; this mode creates no RAM attachment. It sets the standard proxy environment variables for the command. The default private-network hard limit remains active. A `network: true` request and `egress_origins` cannot be combined. Approval applies only to the current command scope and does not authorize an automatic host retry.

The mediator forwards visible HTTP GET, HEAD, and POST requests with a bounded body and checks each new request and redirect destination. Linux HTTPS uses an opaque CONNECT tunnel and macOS HTTPS uses an opaque SOCKS tunnel: Loop checks the target host and port when a new tunnel opens, but cannot inspect encrypted redirects, domain fronting, or traffic sent inside that tunnel. It refuses stronger origin policies that require those guarantees. DNS is resolved by the mediator, without granting the sandbox direct DNS or UDP. On macOS, at most 64 lookups can remain outstanding across all mediators in the Loop process; when that limit is reached, new connections are denied until a lookup returns. A stalled system resolver can retain a worker after its mediator closes, and closure is reported uncertain if the worker has not settled by shutdown. Mediated IPv6, UDP, QUIC, SSH, raw sockets, and clients that ignore the configured proxy are unavailable; a client may also need its own supported proxy and certificate configuration. On macOS, system curl and Apple Git can use the Unix SOCKS path for HTTP(S); `uv` does not support that Unix proxy address. For dependency retrieval with that client, fetch approved artifacts with curl and install from local files with `uv --offline`, or use an independently authorized broader network environment. This gap does not trigger a host retry. An approved endpoint can receive arbitrary data and forward it elsewhere, so an origin grant is meaningful authority to disclose data to that endpoint.

When requesting additional sandbox access, the model can provide a `reason`. The approval prompt shows that explanation and the requested paths, executables, and network or Git scope to the user.

Ordinary shell commands and their children have read and execution access to the platform's system runtime and eligible installed runtime paths. On macOS this includes standard Homebrew tool, library, package and support directories when the installation is present, as well as conventional locally installed binary and library directories. Linux includes its authenticated distribution runtime and loader paths. This gives shell functions, build scripts and dynamic library loaders the same scoped access as the top-level command. Executable names still use the inherited `PATH`. Inspect the presets or manage additional scopes with [`/permissions path`](permissions.md#sandbox-paths). A path grant does not approve the command itself, permit a write or override a hard denial.

For a recognized safe executable named directly in a command, Loop verifies the executable found on `PATH` and can grant access to that file alone. Its directory and neighboring files remain inaccessible. Other tools may need their installation directories. When Loop cannot identify the required scope in the original call, `resolve_executable` accepts one name or a list of the tools needed by the project and returns a separate result and reference for each available tool. Pass the applicable references to `run_command`. Verified package directories can be added automatically; other directories require separate read approval, which can include neighboring files. Lookup does not run the tools or infer which indirect tools a command will invoke. Commands still run inside the sandbox.

For an unambiguous system `make` invocation, Loop can inspect selected literal phony recipes and their prerequisites to prepare the identified indirect tools in the same call. Initial no-op workspace directory changes, safe descriptor redirections, and pipelines with simple literal stages are recognized without changing the command. Workspace interpreter discovery shares a bound of 128 selections across the selected recipes. It follows supported literal interpreter chains, but does not infer a tool selected only from a recipe wrapper’s arguments. Dynamic build rules, environment settings that alter make selection, potentially mutating redirections, complex shell sequences, and selections beyond that bound use the normal explicit-scope behavior; inspect possible effects before retrying a command.

A literal `timeout` or `gtimeout` invocation with a numeric duration can also identify its child command in the original call. Loop requests approval for identified child installation and runtime folders that are not already authorized. Timeout options, expanded durations, assignments used as the child, and ambiguous child paths do not supply automatic discovery.

Loop can also inspect a bounded session scratch script selected as a literal `$TMPDIR` argument to a verified system shell. Simple literal commands can use the same managed-tool and project-runtime discovery as direct commands. Complex shell constructs and ambiguous selections are left to normal explicit-scope behavior. Inspection is advisory; the script can change before execution, and its contents do not authorize host execution, Git writes, or additional manual grants.

For an already requested or granted read root, Loop can prepare directory aliases needed by symlinked `PATH` entries even when a child process selects the executable. Discovery examines up to 1,024 directory entries and 128 matching candidates per command, prioritizing non-system `PATH` directories while preserving executable lookup order. It does not authorize other roots or neighboring data. If an indirect alias falls outside those bounds, a supported explicit executable lookup and reference can identify it for the original scope; inspect the result and any possible effects before another execution.

A workspace script selected directly, or named by a literal path or filename argument relative to the command's working directory, can also use an absolute `#!` interpreter outside `PATH` when its runtime root is requested and approved. When a directly selected script identifies an interpreter through a directory symlink, Loop can request that directory's target together with other requested read roots in the original call; this grants reads to neighboring files in that directory. A workspace-selected executable or interpreter linked directly to an external file can suggest the file's containing directory. A directly selected workspace executable can suggest a linked external directory when no explicit read root was supplied. An existing root that covers the executable or interpreter is reused. If support files lie outside the identified directory, they require a separately approved scope. For a command sequence, automatic root identification covers a literal leading script path, including a wholly quoted path; it does not infer new roots from later commands or shell-expanded executable words. It also follows a literal first argument when an unchanged, complete workspace POSIX-shell launcher consists solely of a quoted `exec` forwarding that argument, including a launcher that prefixes it with `./`. An otherwise unchanged launcher that executes one literal executable with optional literal arguments can also identify that executable, whether it forwards all arguments or discards them. Discarded arguments do not identify additional runtime roots. A forwarded executable name is selected using the inherited `PATH` in order only when the invocation preserves that `PATH`; an explicit executable path does not depend on it. A chain of launchers that forward all arguments can be followed while the selected argument prefix remains literal. Other launchers need an explicit root when their runtime cannot otherwise be identified. Loop inspects at most 4,096 bytes of each candidate single-link script and prepares aliases into the approved root in the same call. It follows bounded workspace interpreter chains; the operating system must also support executing the chain. Argument paths and filenames are discovery hints, not authorization; shell-expanded arguments and further runtime roots are not inferred.

For a selected workspace script with a simple ASCII `#!/usr/bin/env NAME` or `#!/usr/bin/env -S NAME` shebang, Loop can identify `NAME` through the unchanged inherited `PATH`, preserving its order and requesting any needed runtime scope before launch. An explicit interpreter path containing `/` is resolved from the command's working directory without searching `PATH`. The `-S` form may include simple literal interpreter arguments. The name or path must end within the first 126 bytes after `#!`, because some kernels truncate longer interpreter lines. Environment assignments, expansion, quoting, escapes, and other `env` options require an explicit scope when the runtime is not otherwise available. The operating system's `env` implementation must support the shebang form used by the script.

The bounded shell-forwarding discovery also works through these `env` forms when the selected executable resolves to Loop's system shell. Direct system-shell shebangs can include one `-e`, `-f`, or `-u` option group or `--`; the `env -S` form also supports multiple such option groups. The complete shebang must fit within the first 126 bytes after `#!`. A different executable, even one with the same name, is not treated as that shell; other options use the usual explicit-scope path when needed.

For an installation the project does not identify, the owner can override the search path and literal runtime settings in workspace configuration. Additional readable directories can also be managed with `/permissions path`. If a tool needs another path spelling for a granted directory, declare the exact symlink in `tools.sandbox_path_aliases`. This works through shell scripts, build tools and package managers without depending on their invocation syntax. Prepare dependencies separately when synchronization needs writes, caches or networking. [Sandbox execution settings](configuration.md#edit-settings-while-loop-is-running).

On supported Linux installations, Loop can verify shared files whose other hardlink names are inside the account home. Lookup follows the approved read scope and any hard readable-root limits. The trusted backend checks file names, devices and inodes, and skips protected paths. The command sees the shared files through its approved paths, where they stay read-only even with project writes enabled. Every link must be accounted for. A missing, protected or unverifiable link prevents admission. An administrator can prohibit account metadata lookup.

Hardlink verification on macOS and Linux has a preparation deadline and a limit of 100,000 directory and hardlink records per inventory, including retries within that inventory. The Linux receiver classifies protected paths during the same walk that accounts for hardlinks. Ordinary files with one link consume no file records and are checked again for new links before launch. Metadata lookup outside the sandbox view retains only matching names and the directories leading to them. The evidence is held in memory for the current request. Loop refuses launch when verification exceeds either limit.

Installed package metadata can identify candidate dependency directories. A saved path grant or the command's scoped approval controls access to those directories. Neighboring files are included in a directory grant. System runtime directories remain available to shell children without a command-name allowlist.

Approved sandbox writes go directly to the checkout. Concurrent commands can change the same workspace and session working files, and Loop does not roll back shell changes. A complete benign hardlink set inside the admitted data roots is usable on macOS when every alias has the same read/write authority. An alias set spanning writable and read-only roots refuses admission, and copying the file creates an independent writable inode. On Linux, existing benign linked files remain readable and executable, but become read-only. Loop binds individual files whenever the Linux launch fits the available descriptor slots and argument bytes. If needed, it makes selected containing directories read-only until the mounts fit. This can also affect ordinary siblings. An explicitly granted write root or exact write path stays outside any grouped directory. Loop refuses launch if it cannot fit a plan within those constraints. New ordinary same-root links remain available. Linux bind boundaries can require copying across roots instead of linking. Direct file tools accept fully accounted benign aliases, bind their approved identities, and replace or delete only the selected name. Incomplete or protected alias sets remain unavailable to those tools.

On Linux, a trusted hard-denied directory is masked by an empty, read-only mount. Incomplete hardlink sets are admissible only when every observed name is hidden under a denied directory mask. Hidden entries are excluded from the command’s `PATH`; visible entries retain their order. A command that explicitly requires a hidden path fails before execution. [Native alias admission](permissions.md#boundaries).

Loop creates `$LOOP_OUTPUT_DIR` in private session scratch before each admitted command launches. It is unique to that attempt and stays under `$TMPDIR` for the session's lifetime. For a read-only workspace, direct generated files there using the tool's own output settings. The result reports the corresponding file-tool path in `scratch.output_path`. Tools can use the shared session scratch for reusable caches.

Linux provides an attempt-private, size-bounded `/dev/shm` for POSIX named semaphores and shared memory. Commands and their descendants can share these objects within one attempt. See [macOS synchronization](#attempt-local-synchronization) for workloads that depend on named semaphores.

Use `$WORKSPACE_ROOT/...` for workspace files and `$TMPDIR/...` for the conversation's private working files. For example, run `printf draft > "$TMPDIR/report.txt"`, then call `read_text_file` with `path: "$TMPDIR/report.txt"`. Saved shell scripts use those same quoted variables. Programs read `WORKSPACE_ROOT` and `TMPDIR` from their inherited environment and pass the resulting paths to subprocesses; standard temporary-file APIs use the same session directory. Loop passes the supplied command and saved script text through without rewriting it. Declared environment variables are assigned before the command runs. File tools accept the declared prefixes and physical host paths within the configured workspace, session or active skill roots. They perform no general environment expansion, reject traversal outside those roots and apply the same permission and identity checks to either spelling. A Linux sandbox namespace path can differ from the host path; use the declared prefix when the two do not match. `/tmp` is an operating-system pathname; the Linux private mapping described below has session retention, while other uses remain outside that guarantee. Files persist across commands, turns, interruptions, and saved-session resumes on the same machine. Starting or switching conversations selects an isolated directory without removing earlier files. New CLI sessions use private working directories outside the checkout, normally under `~/.loop-scratch`. Loop prefers a path without whitespace when available. Loop keeps those directories across restarts and reopens legacy sessions at their recorded paths. In-memory library stores retain files for the store's lifetime. Session exports do not include working-file contents, but recorded tool results can contain working-file data. Library integrations must keep session storage outside shared workspace or approved read roots to retain isolation between conversations. Durable generation bindings prevent silent recreation when bound data is missing or unsafe; such sessions fail with an explicit recovery error. Valid existing directories are adopted in place without copying. Fresh agent-data generations allow ordinary basenames such as `.loop`, `.ssh`, and `Library`; existing restricted generations keep their private-name restrictions until explicitly discarded. Native link checks, workspace controls, and outside-root protections remain active. Copy deliverables into the workspace.

The `/skills/<name>` root returned when a skill is activated addresses files through the file tools; it is not a shell pathname. Shell commands that access a skill use its physical path with the normal read authorization and native restrictions. If a referenced skill is deactivated or replaced before command admission, including while approval is pending, the command does not launch. Changes to unrelated skills do not invalidate the command; changes after admission affect future commands. Library callers should use `InstructionsManager.deactivate_skill()` for revocation or reacquire its `skill_manager` property after an instruction refresh; a retained manager reference may refer to a previous catalog.

On Linux, eligible fresh session scratch has a separate private `/tmp` subtree. A file written as `/tmp/report.txt` is available to later commands at that path and to file tools as `$TMPDIR/loop-conventional-tmp/report.txt`. The subtree shares the session's retention, discard and filesystem storage limits; Loop does not impose a separate quota. The private mapping is unavailable for restricted or unbound scratch and when it would overlap an approved workspace, tool or runtime path. An existing unsafe or shared backing directory is refused. On macOS, literal `/tmp` does not refer to the private session directory, and sandboxed access to the host's shared temporary files is denied by default. Use `"$TMPDIR/..."` for portable temporary files.

The command environment sets `HOME`, `TMPDIR` and `XDG_CACHE_HOME` to session-private scratch paths. Preserve these values when constructing a subprocess environment, and quote paths passed as shell text. Tools can open their private paths directly, including build tools that read input from a temporary file. Tools invoked by a build may still need their own executable grants. #### macOS shell and account limits

Loop runs top-level POSIX command text with the system's bundled Dash shell, which supports here-documents from a read-only working directory. Executable scripts keep their shebang interpreters, and explicit shell invocations run the selected executable. Apple's Bash 3.2 ignores `TMPDIR` for here-documents and here-strings. Its temporary-file fallback can fail in a read-only working directory. Supply data to legacy Bash through standard input or a file under `$TMPDIR`. If a script requires a compatible installed Bash, invoke it explicitly or use the declared `PATH` for calls that already select Bash by name. An absolute `/bin/bash` shebang selects Apple's Bash regardless of `PATH`. [Apple Bash redirection](https://github.com/apple-oss-distributions/bash/blob/main/bash-3.2/redir.c#L345-L381), [Apple Bash temporary directory selection](https://github.com/apple-oss-distributions/bash/blob/main/bash-3.2/lib/sh/tmpfile.c#L54-L89).

On macOS, a command that clears its private `HOME` can fail to find its login home through stock account lookup. The agent can request `account_lookup` in `runtime_services` for a command that needs the host Open Directory account service. The approval explains the service’s scope. It may return account and group records including directory-supplied password fields, and it may contact a network directory even when the command has no direct networking. Inherited `HOME` stays private. General network approval alone allows native DNS and grants no account-service access. [Workspace permissions](permissions.md#optional-sandbox-capabilities).

Native advisory ownership locks serialize cooperating harness operations on the same saved session; independent sessions can run concurrently. Recovering abandoned interactions requires ownership, so a competing loader cannot revoke a live request. Blocking prompts and confirmations retain the selected session's ownership through durable settlement, including idle command requests. Cancellation during registration or while input is pending revokes the matching request without granting a late approval; ownership remains held until revocation settles. Ordinary idle input still permits session selection. Locks close on exec and live outside the command-writable leaf. Ownership does not revoke old writable descriptors. Library callers can retire working files with `SessionManager.discard_working_directory()`; it commits a fresh generation before cleaning the validated retired root and reports incomplete cleanup. Child processes inherit the sandbox restrictions. Linux verifies descendant cleanup before returning a successful result. When its native receiver observes a full client disconnect during spawn or supervision, it exits; systemd sends SIGKILL to remaining service processes, and installation capacity remains reserved until the cgroup is empty. A lost client connection does not itself establish cleanup. On macOS, detached children can outlive command completion and cleanup while retaining their restrictions. Neither deletion, reopening nor an ownership lock establishes descendant termination or an exclusive-writer guarantee. Working files are ordinary retained filesystem state, without an atomic snapshot of them and the conversation database.

If the Linux receiver observes control input while spawn is stalled, it exits after a brief grace period, including when the client has half-closed its write side. An empty write half-close is not cancellation. The client reports an uncertain outcome because the receiver cannot confirm cleanup.

Logical path metadata reduces incidental disclosure of host locations, but does not guarantee path secrecy. Captured command stdout and stderr are preserved in previews, continuations and recorded tool results, subject to capture and decoding limits; commands such as `pwd` can expose physical paths to the model. File contents, user input and approved communication can also contain paths or other sensitive data. Existing credential filtering at the model boundary still applies; a command stream changed by that filtering has `payload_redacted: true` in the model-facing result, while the stored result remains unchanged. Previously saved results and continuations remain as recorded; their original output cannot be recovered if it was rewritten. The sandbox shares the host kernel and provides less isolation than a virtual machine. It does not protect against a malicious program already running outside the sandbox under your account, or impose strict limits on command memory use or process counts. Offline commands can still disclose readable data through output sent to the model or permitted local communication. A general `network: true` grant allows general connections; a mediated origin grant applies only at the visible HTTP request or HTTPS tunnel boundary described above.

Loop decides declared filesystem capabilities before launch. Shell inspection can explain likely effects, but cannot grant workspace or Git writes. Commands with an approved directory write capability can modify ordinary files there without a separate prompt for each file.

`run_command` always requires native confinement. An unavailable, denied, timed-out, or ambiguous result never executes the command on the host. The separate `request_host_command(command, reason, cwd)` tool is available only when trusted `app.allow_direct_host_execution` is enabled. It shows the exact source, cwd, agent-supplied reason, unrestricted authority and repeat-effects warning before one-run consent or an exact remembered grant. Eligible YOLO requests may run without a prompt, but cannot enable the gate, override host denies or save a grant. Host results are marked `boundary: host` with an unrestricted-authority notice. See [host authorization](permissions.md#direct-host-authorization) for scopes and limitations. Fixed trusted `/sandbox` management remains a separate human operation.

| -------- | ------------------------------------------------------------------------------------------------------------------------- |
| macOS    | Startup checks that Seatbelt allows a workspace write and blocks a protected read and an outside write.                   |
| Linux    | Requires an authenticated native installation and an enforcement probe. Loop checks the installation before each command. |

Sandbox availability depends on the operating system’s enforcement capabilities and a successful startup check. Loop refuses sandboxed execution when those requirements are not met.

### Host-loopback service publication

`run_command(ingress_port=8123, ...)` requests one `127.0.0.1:8123` listener for the current live attempt. `network.ingress` defaults to `ask`, independently of HTTP egress, and approval occurs before publication. The prompt binds the port, attempt, target and policy lifetime. Local-network hard denials still prohibit this transport. Ingress cannot be combined with general networking, mediated egress or an interactive terminal, and it cannot publish on a LAN/public interface.

On Linux, start a server at `127.0.0.1:$LOOP_INGRESS_PORT` inside the private namespace. A sealed trusted worker receives accepted host clients through a private control channel and connects only to that private port. The agent and its children inherit the full descriptor-receipt denial after worker setup and cannot access the handoff channel. An installed receiver without this capability requires `/sandbox refresh`.

On macOS, use `exec` to replace the foreground shell with a Unix service listening at `$LOOP_INGRESS_SOCKET`. Ingress acquires the checked local-IPC volume automatically. The host listener exchanges bytes through a separately Seatbelt-confined connector, which may connect only to the exact Unix endpoint and checks the retained foreground peer PID before forwarding bytes. A client that connects before the service listens can reconnect once the Unix endpoint is ready. A terminal connector or foreground identity failure ends publication and reports the failure. TCP-only services are unsupported. Scoped publication grants no payload IP networking. Configure a compatible server's Unix listener instead of requesting broader network access.

Completion, cancellation, policy revision or loss of the bounded authority lease closes the listener and active relays. The port is unavailable afterward; a new attempt requires its own scope and endpoint. Ordinary host clients can reach the published service while authorized. Applications remain responsible for authenticating those clients if their protocol requires it.


## Manage the Linux sandbox

The interactive Linux app provides `/sandbox` commands. Check status before running commands that depend on native enforcement:

```text
/sandbox status
/sandbox status details=true
```

The first command gives a short installed, not installed, or needs attention result. The detailed form inventories managed paths, systemd units, and loaded AppArmor profiles. It is read-only and does not authorize removal. If Loop cannot safely inspect part of the installation, it reports that part as unknown.

| Command              | Effect                                                                   |
| -------------------- | ------------------------------------------------------------------------ |
| `/sandbox install`   | Set up a fresh installation, cleaning authenticated partial state first. |
| `/sandbox refresh`   | Alias for reinstall. Reviews removal and installation separately.        |
| `/sandbox uninstall` | Remove an authenticated, idle installation.                              |
| `/sandbox reinstall` | Run uninstall, then install, with separate consent for each step.        |

These management commands require fresh consent, a real terminal, and administrator authentication. The responsive UI first requests exclusive terminal access; press Enter or use `/respond` to hand it over. The normal editor stays suspended until the management operation settles, and the operation still requires its own fresh consent. Library and headless calls cannot elevate, and setup does not install OS packages. Refresh verifies its replacement helper before removing the current generation and stops if removal fails. You can retry after a failure; Loop verifies the current installation before proceeding. Recorded uninstall does not need a helper download. Recovery of a partial installation without a management record checks any protected staged helper and the remaining files against the package being reviewed; if other files belong to another package version, retry with the original package before updating. Loop refuses removal when descendants are running, native state is ambiguous, files have changed, or private inventory cannot be verified. An incomplete operation is reported as a management failure with attempted steps, a short reason, and current status; native execution remains unavailable until setup is healthy.

The Linux runtime needs a fixed Bubblewrap 0.12.0 or newer, enforcing AppArmor, libapparmor, libseccomp, Python 3, and systemd/cgroup v2, together with the host's policy parser and management tools. Stock Ubuntu 24.04 supplies an unsafe Bubblewrap 0.9; on Ubuntu 24.04 `x86_64` and `aarch64`, `/sandbox install` downloads the reviewed Ubuntu 26.10 Bubblewrap 0.12 package before asking for consent or administrator authentication. Loop verifies Ubuntu's signed release and package index with the protected Ubuntu archive keyring, checks the package and executable against Loop's provenance manifest, checks ELF architecture and host compatibility, and passes only the verified executable to protected setup. The download needs access to the official Ubuntu archive and fails closed when unavailable; privileged setup does not fetch code or install system packages. An administrator-provided, root-protected fixed helper at `/usr/local/bin/bwrap` takes precedence. Loop copies the selected helper into its own root-owned installation and leaves `/usr/bin/bwrap` and the distribution package untouched. The installation restores volatile policy and service state after reboot. Ordinary compatible Loop updates do not require another installation; Loop distributors maintain the managed helper manifest and must ship a reviewed update when its source becomes unsuitable. Applying a new managed helper or repairing invalidated native authority requires the normal confirmed `/sandbox refresh`; uninstall removes only the authenticated Loop generation and never changes the Ubuntu package. Recorded uninstall works without archive access. An unrecorded partial installation is removed only when its protected files match the reviewed catalog; otherwise Loop leaves them for administrator inspection. Loop uses separate file descriptors for repeated mount sources. Workspaces with many protected or private entries may exceed the operating system's open-file limit; Loop refuses mount preparation before starting the command when that limit is exceeded. Loop does not automatically run the command on the host. Offline commands use a separate network namespace. The receiver exposes selected authenticated system files, including resolver data, public CA bundles and the distribution’s `/etc/mime.types` when present. A runtime that enumerates the public CA directory can request that directory as an explicit read root. This does not grant network access. Refresh an older receiver to use the updated system-file list.

On qualified Linux, an ordinary offline command can use IPv4 and IPv6 TCP and UDP loopback with its own descendants in one private network namespace. Start the server and client in the same command attempt; a later command gets another namespace. That namespace has no host or external network interface, route, bridge, forwarding path, or host proxy. A user `local-network deny` limit or administrator `deny_local_networks` restriction prevents the payload from creating IPv4 or IPv6 sockets. If exact HTTP(S) mediated egress is approved at the same time, the payload may create only IPv4 stream clients for its trusted attempt-bound loopback proxy; `bind`, `listen`, IPv6, and UDP remain denied. The proxy checks approved destinations independently and does not grant access to host-local services. A general network grant is unavailable while local networking is denied because it would expose host loopback. These local controls require an installed receiver with the matching native filter; refresh an older installation before using a local deny.

Linux sandboxed commands can use `NETLINK_ROUTE` for interface discovery. Other socket families and netlink protocols are unavailable, including VSOCK and userspace netlink, even when network access is approved. Pathname and abstract Unix-domain socket creation and datagram socket pairs are unavailable; ordinary pipes and connected Unix stream and sequenced-packet socket pairs remain available. The private network namespace isolates abstract Unix names; filesystem and socket-family controls deny access to host Unix sockets. An installation without these socket-family restrictions refuses sandboxed execution and requires a checked `/sandbox refresh` to install the protected enforcement update. On qualified macOS, `local_ipc: true` requests pathname Unix stream and datagram sockets beneath `LOOP_LOCAL_SOCKET_DIR`. The `network.local` decision defaults to `allow` and applies before setup. Loop refuses a combined `local_ipc: true` and `network: true` request before approval. Backend selection and ordinary offline commands create no attachment. Loop creates that private directory on an owned 8 MiB RAM filesystem separate from the workspace and scratch, so an agent cannot relocate a host socket into the allowed path. Configure tools to place their sockets there; ordinary `$TMPDIR` remains session scratch and is not a socket endpoint. Unix socket paths retain macOS's length limit, so tools using long socket names may need a shorter name. The directory is removed after the attempt, and a later attempt cannot connect to it. Overlapping local-IPC and ingress attempts share one checked attachment with separate directories. The final lease attempts checked eject; a failed eject reports uncertainty and prevents reuse until recovery. The path rule denies agent-origin connections to host Unix sockets, host IP loopback and external IP destinations; a user or managed local-network deny removes the local socket grant. A host process that learns the private path may connect inbound to a sandbox listener. This does not grant the sandbox access to host services and does not authenticate the peer for any protocol that needs peer identity. An unsandboxed host peer that knows the private path can deliberately pass a file descriptor to the sandbox. That host-origin delegation is outside the agent-origin isolation guarantee; applications requiring peer identity must authenticate it themselves. If the host cannot qualify the RAM filesystem and a native Unix exchange, Loop omits the local capability while ordinary offline commands remain available. When a failed attachment reports no device, the running Loop instance retains its unique marker and attempts checked cleanup on close. Cleanup requires the exact marked RAM image and verified whole-disk identity. An abrupt Loop termination can leave a mounted or unmounted RAM image until checked manual recovery or reboot. The current macOS backend does not offer scoped TCP or UDP loopback, since a general loopback grant can reach host services. An explicitly authorized general network grant has that broader reach.

#### Attempt-local synchronization

An approved macOS local-IPC attempt without host publication supplies `LOOP_SYNC_SOCKET` alongside the local socket directory. A workload can explicitly select a client that uses this separate Unix stream endpoint for named counters. Loop protects the endpoint and its directory from sandboxed writes and permits outbound connections only to the exact path. Separate attempts with scoped local IPC receive their own endpoint and cannot connect through that grant. The host-side broker handles synchronization data in memory. It offers no file access, process operations, or external network forwarding. Workloads select their own client integration. Local IPC alone keeps raw POSIX named semaphores denied.

Unmodified runtimes such as CPython spawn pools and joblib’s process backend use named semaphores. The agent can request `process_pools` in `runtime_services` for a command that uses them. The approval describes the shared resources. The macOS backend permits the native semaphore API with Seatbelt’s same-sandbox owner filter and the system semaphore-limit query. Names and capacity are shared across attempts and host processes. Live unrelated objects retain their native protection. A command can detect name collisions and may access or unlink another same-user attempt’s object after its owner is gone. Names cannot reliably identify abandoned objects, so the backend leaves them in place. Without the opt-in, threads and pipe-based children remain available. [Workspace permissions](permissions.md#optional-sandbox-capabilities), [Apple XNU semaphore implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/posix_sem.c).

Send one ASCII JSON array per request, followed by a newline, and read its response before sending another. Each request is at most 512 bytes including the newline. A response is `[0, result]` on success or `[errno, null]` on failure. Each of the seven commands uses a case-sensitive name or a connection-owned opaque handle.

| Request | Result on success |
| --- | --- |
| `["create", name, value, maximum]` | Create a named counter and obtain a handle. |
| `["open", name]` | Obtain or retain a handle for an existing name. |
| `["unlink", name]` | Remove the name and return `null`. Existing handles stay valid. |
| `["acquire", handle]` | Decrease the counter and return `true`, or return `false` if empty. |
| `["release", handle]` | Increase the counter and return `true`. A release above the maximum fails. |
| `["value", handle]` | Return the current count. |
| `["detach", handle]` | Drop one reference and return `true`. |

Names contain 1 to 128 ASCII letters, digits, underscores, or hyphens, with an optional leading slash. Counter limits are integers from zero to 2,147,483,647, and the initial value must fit the requested limit. Each attempt supports up to 512 counters and 64 simultaneous client connections, and each connection can retain up to 4,096 references to a counter. Disconnect drops all of that connection's references. An unlinked counter is released when its final reference closes. Command completion or cancellation retires the broker and every reference even if a detached descendant survives. A controller death closes the socket descriptors and loses the in-memory namespace. A restarted Loop creates a fresh endpoint and namespace. The existing macOS RAM attachment can require separate checked cleanup after abrupt controller termination.

Linux sandboxed commands cannot use `recvmsg` or `recvmmsg` because those calls can receive file descriptors with host authority. Some programs use them for ordinary network data: for example, `dig` over UDP fails inside the sandbox, while `dig +tcp` works when network access is approved.

Linux preserves a selected, authenticated system executable's `/etc/alternatives` link without exposing the rest of that directory. A selected system link that needs another unmounted path cannot be prepared; requesting an authorized scope that contains the required path may make it available.

Linux TLS clients can list the sandbox's `/etc/ssl/certs` directory offline. In the default scope it contains only the authenticated public CA bundle when installed. Individual host certificates and private keys stay outside this mount. Hard path denials also apply to the bundle and its directory.

Automatic boot recovery requires the `/run` filesystem to support unnamed temporary files and atomic `linkat` publication. If those facilities are unavailable, Loop cannot restore the installation and refuses sandboxed execution.

Loop versions from before that transition use an older snapshot-matching rule and can reject the new installation even when their command protocol is unchanged. Use an updated Loop client with the new installation; refreshing the healthy installation solely for an older client would replace the new architecture.

Removal refuses while sandboxed commands or their descendants are live. An attempted removal can still block new commands and invalidate results from commands already running. After commands finish, retry removal or refresh in the main app. Loop keeps those commands confined and does not retry them automatically.

Linux creates request-specific sandbox profiles and automatically reclaims them after their owning Loop service and its descendants have exited. Completed requests do not accumulate toward the profile limit. When all slots are occupied by live commands, a new request waits within its existing deadline for capacity. Temporary contents remain isolated and search copies remain read-only. Loop protects its own workloads during profile retirement; another application must not transition its processes into Loop's managed profiles, because removing such a profile can leave those processes unconfined.

## Search files

`search_text` searches folder contents or selected files. It supports smart-case literal matching, regular expressions, case control, Git-style globs, neighboring lines, and a global result limit. Folder searches honor ignore rules, skip binary files and symbolic links, and return paths relative to the selected folder.

When trusted ripgrep is available, Loop runs it with fixed arguments inside a read-only native sandbox. The helper receives only the files selected and authorized by the file tool; it cannot browse other workspace or private files. Otherwise, Loop uses a bounded Python regex matcher. The two matchers have different regex dialects. Patterns are limited to 1,000 characters and searches to 30 seconds; long lines and results can be truncated. A changed native authority causes search to fail instead of switching to the Python matcher.

The optional `tools` extra installs ripgrep in the workspace virtual environment for shell commands. That workspace-writable binary is not trusted as a helper for public search.

## File and web results

Direct file tools apply Loop's hard resource policy before opening host files or mutating them. `list_folder` follows `.gitignore` and `.agentignore` when discovering files; an explicit request can name an ignored path only when it is not hard-denied. Environment-value files and trusted private designations stay inaccessible through read, list, search, edit, delete and cached continuation operations. Public environment templates remain accessible unless designated private. See [resource boundaries](permissions.md#boundaries) for classification and alias limits. Text reads report source size, range, truncation, and continuation position. Results larger than 20 KiB are stored outside conversation history and returned as a preview with a `read_cached_content` handle; cached file results recheck the current policy for their original sources.

Web fetches require authorization and do not follow redirects implicitly. Cached web handles keep their source metadata when a session resumes. After a handle expires, fetch the content again with new network authorization. Other cached artifacts stay local to the process.
